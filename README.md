# stat·plan

Открытый инструмент для планирования и валидации A/B тестов. Помогает продуктовым менеджерам и аналитикам пройти полный цикл — от формулировки гипотезы до пост-анализа — без необходимости вручную выбирать статистический критерий и без риска получить методологически сломанный тест.

## Зачем

A/B-калькуляторов много, но почти все упираются в две проблемы:

1. **Методология может быть неприменима к данным пользователя.** Калькулятор не знает, что у тебя right-skewed распределение, zero-inflation в ARPU или sample ratio mismatch — и спокойно предлагает t-test.
2. **Пользователю нужно отлично знать статистику**, чтобы выбрать критерий, понять ассумпции, оценить мощность.

stat·plan решает это через двухслойный подход:

- **Что можно — делаем на клиенте, в браузере.** Сборка тест-плана, базовая проверка данных, генерация ноутбука, независимая перепроверка результатов.
- **Что требует серьёзных вычислений или доступа к продакшен-данным — уходит в генерируемый Jupyter-ноутбук**, который пользователь запускает у себя.

## Для кого

- **Продуктовые менеджеры** — заполняют бриф, получают тест-план и готовый ноутбук, идут обсуждать спорные пункты с аналитиком.
- **Аналитики** — получают структурированный артефакт для ревью, могут редактировать md-файл и загружать обратно.
- **Небольшие команды без штатного аналитика** — получают разумные методологические дефолты и предупреждения о подозрительных решениях.

## Принципы

1. **No backend.** Всё работает на статических файлах GitHub Pages. Все артефакты — на клиенте, в localStorage между шагами при необходимости.
2. **Артефакты — обычные файлы.** md и ipynb, которые можно открыть, отредактировать, закоммитить, отправить в Confluence. Никакого vendor lock-in.
3. **Тул не принимает продуктовых решений.** Не говорит «катить или нет». Проверяет полноту плана и методологическую консистентность, но финальное решение всегда за человеком.
4. **Структурная оценка, не оценка качества мысли.** Скоринг проверяет наличие обязательных секций и консистентность выбранных методов — не пытается оценить «хороша ли твоя продуктовая гипотеза».
5. **Открытость данных.** Пользователь видит, какие правила применяются для оценки и почему. Никаких «black box» рекомендаций.

## Основной флоу

```
[Старт: выбор пути] → БРИФ → ТЕСТ-ПЛАН → КОНСТРУКТОР → АНАЛИЗ → READ-OUT
```

На старте — развилка: «Начать с брифа» или «Загрузить готовый план». Второй вариант пропускает бриф и попадает сразу на конструктор ноутбука. Бриф при этом не теряется — восстанавливается из YAML frontmatter плана.

Детали — см. [FLOW.md](FLOW.md).

## Что НЕ делаем (явные не-цели)

- Не интегрируемся с BigQuery / Amplitude / Mixpanel — пользователь сам выгружает csv.
- Не храним историю тестов — каждый прогон stateless. Если нужна история — пользователь складывает md/ipynb в свой git.
- Не делаем sequential testing с always-valid CI в первой версии (хорошая идея на будущее).
- Не делаем библиотеку прошлых тестов / поиск по похожим экспериментам.
- Не делаем авторизацию, шаринг, командную работу.

## Технический стек

- React 19 + Vite + Tailwind + react-router-dom (HashRouter)
- Vitest для unit-тестов math/parse-логики
- Деплой: GitHub Pages через GitHub Actions
- Подключаются по мере нужды: js-yaml (парсинг YAML frontmatter), papaparse (csv), simple-statistics (расчёты), recharts (визуализации), JSZip (read-out пакет), html-to-image / html2pdf (экспорт)

Pyodide отвергнут — 10MB рантайма ради scipy не оправданы (ADR-009).

См. [docs/context/ARCHITECTURE.md](docs/context/ARCHITECTURE.md) для деталей и [docs/context/decisions-log.md](docs/context/decisions-log.md), особенно ADR-001 и ADR-010.
