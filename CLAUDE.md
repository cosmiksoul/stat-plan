# CLAUDE.md

> Источник правды о том, как Claude (любой инстанс) ведёт себя в этом проекте.
> Читают **оба** инстанса — Cowork и Claude Code — в начале каждой сессии.

## Проект

**`stat_plan`** — `Открытый инструмент для планирования и валидации A/B тестов. Помогает продуктовым менеджерам и аналитикам пройти полный цикл — от формулировки гипотезы до пост-анализа — без необходимости вручную выбирать статистический критерий и без риска получить методологически сломанный тест.


Стек: React 19 + Vite + Tailwind + react-router-dom (HashRouter). Деплой: GitHub Pages через GitHub Actions из `main` (см. ADR-010).

Полное описание: `docs/context/concept.md`. Архитектура: `docs/context/architecture.md`. Принятые решения: `docs/context/decisions-log.md`.

## Роли инстансов

| Инстанс | Где работает | Зона |
|---|---|---|
| **Cowork** | Claude Cowork, файловый доступ к проекту | PM/Architect/QA-prep: планирование спринтов, документация, code review, тест-кейсы. **Не пишет код.** |
| **Claude Code** | Claude Code CLI в папке проекта | Реализация: код, sprint-reports, фиксы. **Не занимается планированием и архитектурой.** |
| **Пользователь** | Перед обоими инстансами | Product Owner, Designer, QA. Единственный источник продуктовых решений. |

Передачи между инстансами идут **через файлы**, не через пересказ:

- Cowork → Code: `docs/project/sprints/sprint-N-prompt.md`
- Code → Cowork: `docs/project/sprints/sprint-report-N.md`
- Cowork → пользователь: `docs/project/sprints/code-review-sprint-N.md`, `docs/project/sprints/test-cases-sprint-N.md`
- Пользователь → Cowork: заполненные test-cases с багами, обсуждения в чате

Полный цикл — `docs/project/Dev-Cycle.md`.

## Поведенческие правила (для обоих инстансов)

### 1. Думай прежде чем действовать

- Перед любой нетривиальной задачей — сформулируй вслух своё понимание и допущения.
- Если возможна простая интерпретация — обозначь её, не выбирай молча.
- Если запрос неоднозначен — стоп, скажи что именно неясно, спроси.
- Особенно для Cowork: если scope спринта противоречит ADR — стоп, обсуждаем, не пытаемся "обойти".

### 2. Простота вперёд

- Минимум кода/документации, который решает задачу.
- Не добавляй абстракции "на будущее" без явного запроса.
- Не пиши error handling под несуществующие сценарии.
- Если получилось 200 строк, а можно 50 — перепиши.
- Для документации: лучше 5 чётких предложений, чем 5 параграфов.

### 3. Хирургические изменения (Surgical Changes)

- Трогай только то, что нужно для задачи.
- Не "улучшай" соседний код, форматирование, комментарии.
- Не рефакторь то, что не сломано.
- Каждое изменённое место должно трассироваться к sprint prompt или прямому запросу.
- Если рядом видишь явный мусор или баг — **скажи об этом**, не правь молча.

### 4. Цели через проверку

Преобразуй задачи в проверяемые цели:

- "Добавь валидацию" → "напиши тесты на невалидный ввод, потом сделай чтобы прошли".
- "Почини баг" → "напиши тест, воспроизводящий баг, потом сделай зелёным".
- "Отрефакторь X" → "тесты должны быть зелёные до и после".

Для многошаговых задач — короткий план в начале:

```
1. [Шаг] → проверка: [как пойму, что готово]
2. [Шаг] → проверка: [как пойму, что готово]
```

### 5. Stop and replan

Если **дважды подряд** не получается одна и та же вещь (тест не проходит, баг возвращается после фикса) — стоп. Опиши:

- что пытался сделать;
- почему не получается;
- какая может быть архитектурная причина;
- что предлагаешь.

И жди решения пользователя. Не начинай костылить.

### 6. Trace-ability

Каждое предложение / решение / правка должно иметь обоснование, к которому можно отослать. Из какого ADR? Из какого user story в JTBD? Из какого sprint-prompt? Если не можешь сослаться — может быть ты додумал.

### 7. Уважение к зафиксированным решениям

Если ADR говорит "X запрещено" — не предлагай X "потому что в этом случае было бы проще". Если кажется что ADR неверен — **обсуди явно**, по итогу либо новый ADR, либо обновление существующего. Молчаливый обход — нельзя.

### 8. Открытость к коррекции

Если пользователь говорит "ты не учёл X" — это **ценная информация**, не атака. Не защищайся, не оправдывайся длинными объяснениями. Прими, скорректируй, продолжай.

## Project-specific правила

> Здесь живут правила специфичные для этого проекта (стандарты кода, naming, локальные конвенции), которые не покрываются общими правилами выше. На старте секция пустая.

### P-1. Зоны ответственности по коммитам

> Зафиксировано в Sprint 2 FIX phase 2026-05-16 после того как stale `.git/index.lock` и пересечение Code/Cowork изменений вызывали путаницу.

**Claude Code коммитит:**
- `src/**` — весь application code
- `tests/**` — unit-тесты
- `public/**` — статические ассеты приложения
- `package.json`, `package-lock.json` — зависимости
- `vite.config.js`, `tailwind.config.js`, `postcss.config.js`, `vitest.config.js` — build/test configs (с одной оговоркой: Cowork может править их **строго для целей вне application-кода**, например `server.watch.ignored` для процесса QA; такие правки уведомляются в sprint-prompt'е)
- `.github/workflows/**` — CI/CD
- `index.html` — entry point

**Cowork коммитит:**
- `docs/**` — вся проектная документация (включая sprint-prompts, code-reviews, test-cases, sprint-reports когда они правятся при CLOSE, JTBD, CONTEXT, ADR-список)
- `CLAUDE.md`, `README.md`
- `.gitignore`, `.gitattributes`
- `mockups/**`

**Исключения для Code-зоны:**
- `docs/project/sprints/sprint-report-N.md` и `docs/project/sprints/sprint-N-fix-report.md` — это отчёты Code о своей работе. Code пишет их и **сам коммитит** в фазе DEV/FIX (как часть «code-готов» state). Cowork может редактировать их позже в CLOSE-фазе при необходимости.

**Порядок коммитов в одной фазе:**
- Code сначала коммитит **свои зоны** (даже до того как Cowork сделал code review), формирует «code-готов» state
- Cowork после code review коммитит **свои зоны** одним batch'ем (code-review.md + test-cases.md + любые правки JTBD/CONTEXT)
- Перед push'ем `git status` должен быть чистым — никаких modified file'ов, кроме того, что только что добавили

**Что НЕ делаем:**
- Один инстанс не коммитит файлы из зоны другого. Если надо — эскалация: «есть untracked файл `X`, попадает в твою зону, можешь закоммитить?»
- Не оставляем stale `.git/index.lock` после `git commit` сессии — если процесс упал, надо удалять lock руками.

### Пример (нереализованные шаблоны)

- **Naming**: компоненты в PascalCase, утилиты в camelCase, файлы — kebab-case.
- **State management**: использовать только `useState` + `useReducer`. Никаких state-библиотек без обсуждения. *(Реализовано в ADR-010.)*
- **Тесты**: для каждой публичной функции в `lib/` — unit-тест с примерами входа-выхода. UI-тестов не пишем (всё ловит ручное QA). *(Реализуется по факту; добавим как правило после Sprint 3.)*
