# Concept — stat·plan

> Что за продукт, для кого, зачем. Стабильный документ — меняется редко, только по обсуждению.

---

## Что это

**stat·plan** — открытый клиентский инструмент для планирования и валидации A/B тестов, который проводит продуктового менеджера через бриф, генерирует тест-план и Jupyter-ноутбук под него, и независимо валидирует результаты после прогона.

A/B-калькуляторов в интернете много, но почти все упираются в две фундаментальные проблемы. Первая — выбранная методология может оказаться неприменима к данным пользователя: калькулятор не знает про right-skewed распределения, zero-inflation в ARPU или sample ratio mismatch, и спокойно предлагает t-test. Вторая — чтобы выбрать критерий и понять ассумпции, пользователю нужно отлично знать статистику. stat·plan решает обе через дерево вопросов с минимальным ветвлением, структурную оценку плана и генерируемый ноутбук с правильным набором проверок под конкретный сценарий.

Принципиально проект **не пытается быть SaaS** — нет логина, бэкенда, истории тестов. Всё работает на статических файлах GitHub Pages, артефакты — обычные md/ipynb/csv, которые можно открыть, отредактировать руками, закоммитить в git, отправить в Confluence. Это и техническое решение, и философское: пользователь владеет своими данными.

---

## Для кого

Основные роли:

- **Продуктовый менеджер** — заполняет бриф, получает тест-план и готовый ноутбук, идёт обсуждать спорные пункты с аналитиком. Главный целевой пользователь.
- **Аналитик** — получает структурированный артефакт для ревью, может редактировать md-файл и возвращать продакт-менеджеру. Не работает в тула напрямую, но является регулярным участником флоу через файлообмен.
- **Небольшие команды без штатного аналитика** — получают разумные методологические дефолты и предупреждения о подозрительных решениях. Не замена аналитика, но защита от очевидных ошибок.

Кого не целим явно: data scientist-ов с продвинутыми методологическими запросами (sequential testing, causal inference), enterprise-команды с собственной A/B-платформой, исследователей за пределами product analytics.

---

## Принципы продукта

1. **No backend.** Всё работает на статических файлах GitHub Pages. Никакого логина, истории, командной работы — это не SaaS, это инструмент.

2. **Артефакты — обычные файлы.** Md, ipynb, csv. Их можно открыть, отредактировать, закоммитить, отправить коллеге. Артефакт = переносимое состояние: загрузил test_plan.md обратно в тул — продолжил с того же места.

3. **Тул не принимает продуктовых решений.** Не говорит «катить или нет». Проверяет полноту плана и методологическую консистентность, считает CI и p-value — финальное решение всегда за человеком.

4. **Структурная оценка, не оценка качества мысли.** Скоринг проверяет наличие обязательных секций и консистентность выбранных методов. Не пытается оценить «хороша ли твоя продуктовая гипотеза» — это не наше дело.

5. **Открытость данных и правил.** Пользователь видит, какие правила применяются для оценки и почему. Никаких «black box» рекомендаций. Все формулы расчётов задокументированы.

6. **Минимум ветвлений в брифе.** Бриф — это вход для PM, не для статистика. 10 вопросов, минимум обязательных полей, дефолты везде где разумно. Сложности (α/power, CUPED, стратификация) спрятаны в «продвинутые параметры».

## Основной сценарий использования

**Типичный путь — с нуля:**

PM получает задачу проверить новую фичу. Открывает stat·plan, на старте жмёт «Начать с брифа». Проходит 10 вопросов: цель → гипотеза по шаблону → тип метрики → имя метрики → baseline → единица рандомизации → MDE → трафик → guardrails → stop & decision rules. На каждом шаге видит расчётный sample size и длительность теста. Опционально загружает csv с историческими данными — тул уточняет baseline и σ.

Получает тест-план в md с оценкой (78/100, два замечания про MDE и стратификацию). Скачивает md, шлёт аналитику в Slack. Аналитик присылает обратно поправленный файл, PM загружает его в тул — оценка стала 92/100. Жмёт «Утвердить план».

На шаге конструктора видит набор ячеек ноутбука с дефолтами под выбранный метод. Включает дополнительно «сегментный анализ». Скачивает analysis.ipynb. Опционально скачивает demo_proportion.csv, чтобы проверить, что ноутбук работает.

Запускает тест в продакшене. Через 5 дней забирает результаты в csv, возвращается в stat·plan на шаг анализа, загружает csv. Видит независимую валидацию: цифры совпадают с ноутбуком, эффект +9.3% rel., SHIP. Скачивает PDF-отчёт с графиками, заливает в Confluence. Жмёт read-out — скачивает zip со всеми артефактами теста.

**Альтернативный путь — с готовым планом:**

Аналитик сам составил тест-план в нашем формате (или скачал чужой). PM открывает stat·plan, на старте жмёт «У меня есть план», загружает md. Попадает сразу на конструктор. Бриф восстанавливается из YAML frontmatter — можно вернуться и посмотреть. Дальше — как в основном сценарии: ноутбук → анализ → read-out.

## Не-цели (что специально не делаем)

- **Не интегрируемся с BigQuery / Amplitude / Mixpanel.** Пользователь сам выгружает csv. Интеграции — это бэкенд, OAuth, поддержка изменений API; противоречит принципу no backend.
- **Не храним историю тестов.** Каждый прогон stateless. Если нужна история — пользователь складывает md/ipynb в свой git.
- **Не делаем sequential testing с always-valid CI в первой версии.** Хорошая идея, но требует серьёзной методологии. Кандидат на v2.
- **Не делаем библиотеку прошлых тестов / поиск по похожим экспериментам.** Это уже SaaS-фича, выходит за scope.
- **Не делаем авторизацию, шаринг, командную работу.** Шаринг — это передать md-файл коллеге. Командная работа — это коммитить артефакты в общий git.
- **Не используем LLM в продакшен-флоу.** Никакого «LLM решает, какой критерий выбрать» — все правила детерминированные и проверяемые. Тул должен быть предсказуемым.
- **Не делаем мобильную версию.** Аналитика в браузере с телефона — нерелевантный кейс.

## Open questions

> Продуктовые вопросы, ещё не решённые. Архитектурные — в `decisions-log.md`.

- **Локализация интерфейса.** Сейчас русский. Проект публичный на GitHub Pages, рассматривается английский или билингва. Решение отложено до момента, когда станет понятен реальный охват.
- **Веса в скоринге плана.** Текущие веса (20/30/30/20 для гипотезы/дизайна/методологии/data peek) предварительные. Возможно, методологическая консистентность должна весить больше — она важнее, чем полнота секций.
- **Стоит ли вообще показывать численный скор 78/100, или ограничиться чек-листом «3 замечания».** Численный скор может создавать ложное чувство объективности. Решим после первых пользователей.
- **Что считается mismatch при валидации результатов.** Пороги расхождения между ноутбуком пользователя и нашим пересчётом — точные числа vs допуск 0.5%.
- **Хранение нескольких тестов параллельно в localStorage.** Сейчас один активный тест. Если пользователи захотят работать с несколькими — решить, делать ли минимальный switcher.
- **CUPED в v1 или v2.** Технически готов, но добавляет сложности в брифе (нужна pre-period колонка). Решим по реальной потребности.
