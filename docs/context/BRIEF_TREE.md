# Brief Tree

Полное дерево вопросов брифа: формулировки, варианты ответов, ветвления, дефолты, маппинг в YAML.

## Принципы

1. **10 обязательных вопросов, минимум ветвлений.** Простота важнее покрытия всех кейсов. Сложные кейсы покрываются "продвинутыми параметрами" — скрытой секцией с дефолтами.
2. **Каждый вопрос задаёт одно значение** (или связанную пару значений типа MDE = число + единица).
3. **Гипотеза идёт второй**, сразу после цели. Сначала пользователь говорит, что хочет проверить, и только потом отвечает на численные вопросы. Это естественный порядок мышления.
4. **Дефолты везде**, где это разумно. Опытный пользователь видит дефолт и идёт дальше, новичок понимает, что значение можно не задавать.
5. **Каждый ответ детерминированно маппится в YAML-поле** `test_plan.md`. Никакой LLM-магии — простой словарь.

## Структура одного вопроса

```javascript
{
  id: "metric_type",
  num: 3,
  required: true,
  title: "Какого типа главная метрика?",
  hint: "От этого зависит выбор статистического критерия",
  type: "single_select",  // single_select | multi_select | text | number | hypothesis
  options: [...],
  default: null,
  yaml_path: "metric_type",
  yaml_transform: (val) => val,
  unlocks: [...],  // какие вопросы открываются после ответа
  validates: (val) => ({ ok: true, message: null })
}
```

## Вопрос 01 · Цель теста

**Формулировка:** «Что мы тестируем?»  
**Подсказка:** «Это не влияет на статистику, но помогает аналитику понять контекст. Выбери ближайшее.»

| Вариант | YAML value | Комментарий |
|---------|------------|-------------|
| Изменение продукта (фича, UX) | `product_change` | дефолт |
| Контент / креатив | `content` | |
| Алгоритм / ранжирование | `algorithm` | |
| Маркетинг / реклама | `marketing` | |
| Другое | `other` | |

**YAML:** `goal_type: <value>`  
**Ветвления:** нет  
**Обязательность:** да

## Вопрос 02 · Гипотеза

**Формулировка:** «Сформулируй гипотезу по шаблону»  
**Подсказка:** «Не оцениваем "качество идеи" — проверяем только структуру. Все четыре слота должны быть заполнены.»

**Шаблон:** `Если [изменение], то [метрика] [направление] на [Δ], потому что [механизм]`

**Тип:** свободный текст с эвристическим разбором на 4 слота.

**Эвристики разбора:**

| Слот | Эвристика | Пример |
|------|-----------|--------|
| Изменение | Текст между «если» и «то/запятой» | "показать новый блок рекомендаций" |
| Метрика | Текст между «то» и глаголом направления | "CR в клик по партнёрке" |
| Направление + Δ | Глагол (вырастет/упадёт/снизится/повысится) + число с % или единицей | "вырастет на 8%" |
| Механизм | Текст после «потому что» | "пользователь увидит релевантные офферы выше fold" |

**Что делаем со слотами:**
- Если найдены все 4 — зелёные галочки, переход разрешён
- Если найдены не все — показываем красные слоты, но переход разрешён (warning, не блокер)
- Слот «метрика» отдельно используется на следующих шагах для подсказки названия метрики

**YAML:**
```yaml
hypothesis:
  text: <raw text>
  slots:
    change: <true/false>
    metric: <true/false>
    direction_magnitude: <true/false>
    mechanism: <true/false>
```

**Ветвления:** нет (но извлечённое название метрики переиспользуется в Q05)  
**Обязательность:** да (любой непустой текст)

## Вопрос 03 · Тип метрики

**Формулировка:** «Какого типа главная метрика?»  
**Подсказка:** «От этого зависит выбор статистического критерия.»

| Вариант | YAML value | Подходящие методы | Подсказка в UI |
|---------|------------|-------------------|----------------|
| Конверсия / proportion (0 или 1) | `proportion` | z_test_proportions, bootstrap | "Бинарная метрика на пользователя" |
| Средняя величина | `continuous` | t_test, welch, mannwhitney, bootstrap | "ARPU, время на сайте" |
| Ratio (числитель/знаменатель из разных юнитов) | `ratio` | delta_method, bootstrap | "CTR, CR на сессию когда юнит — user" |
| Количество событий | `count` | mannwhitney, bootstrap | "Кликов на юзера" |

**YAML:** `metric_type: <value>`  
**Ветвления:**
- `ratio` → раскрывает подвопрос Q03.1 «Числитель и знаменатель»
- Остальные ветвления на этапе подбора test_method (см. матрицу в SCORING.md)

**Обязательность:** да

### Q03.1 (только если ratio) · Числитель и знаменатель

**Формулировка:** «Что в числителе и знаменателе?»  
**Тип:** две текстовых поля.

**YAML:**
```yaml
ratio_components:
  numerator: <text>
  denominator: <text>
```

**Обязательность:** да (если выбран ratio)

## Вопрос 04 · Имя метрики

**Формулировка:** «Как называется главная метрика?»  
**Подсказка:** «Используется в названиях колонок ноутбука и графиков отчёта.»

**Тип:** текст с автодополнением.

**Автодополнение:**
- Если из гипотезы (Q02) удалось извлечь название метрики — подставляем как дефолт
- Иначе — пустое поле

**Дополнительное поле:** `column_name` (как называется колонка в csv) — отдельный input, дефолт = snake_case от названия метрики.

**YAML:**
```yaml
metric_name: <human-readable name>
metric_column: <snake_case column name>
```

**Обязательность:** да

## Вопрос 05 · Текущий baseline

**Формулировка:** «Какое значение метрики сейчас?»  
**Подсказка:** «Можешь указать примерно — на следующем шаге уточним по реальным данным, если загрузишь csv.»

**Тип:** число + единица.

**Единицы в зависимости от Q03:**

| Q03 | Единицы | Дефолт |
|-----|---------|--------|
| proportion | `%`, `доля (0-1)` | `%` |
| continuous | свободная единица (₽, минуты, etc) | пусто |
| ratio | `%`, `доля`, число | `%` |
| count | число на юзера | — |

**Валидация:**
- Для proportion: 0 < value < 100% или 0 < value < 1
- Для остальных: value > 0

**YAML:**
```yaml
baseline:
  value: <number>
  unit: <unit>
```

**Обязательность:** да

## Вопрос 06 · Единица рандомизации

**Формулировка:** «Что мы делим на группы?»  
**Подсказка:** «Уровень, на котором случайно распределяются пользователи между control и treatment.»

| Вариант | YAML value | Комментарий |
|---------|------------|-------------|
| Пользователь (user_id) | `user` | дефолт |
| Сессия | `session` | |
| Кластер (гео, домохозяйство, кампания) | `cluster` | раскрывает Q06.1 |
| Не знаю / решит аналитик | `unknown` | warning при скоринге |

**YAML:** `randomization_unit: <value>`  
**Ветвления:**
- `cluster` → Q06.1 «По какому полю кластеризуем?»

**Обязательность:** да

### Q06.1 (только если cluster) · Поле кластеризации

**Формулировка:** «По какому полю кластеризуем?»  
**Тип:** текст.

**YAML:** `cluster_field: <text>`

## Вопрос 07 · MDE (Minimum Detectable Effect)

**Формулировка:** «Минимальный эффект, который имеет смысл ловить»  
**Подсказка:** «Меньший эффект тест не "увидит" с заданной мощностью. Слишком маленький MDE → нереально длинный тест.»

**Тип:** число + единица.

**Единицы:**

| Вариант | YAML value | Когда выбирать |
|---------|------------|----------------|
| Относительный % | `relative_percent` | дефолт; "конверсия вырастет на 8% относительно baseline" |
| Абсолютные п.п. | `absolute_percentage_points` | только для proportion; "конверсия вырастет на 0.3 п.п." |
| Абсолютная величина | `absolute_value` | для continuous; "ARPU вырастет на 50₽" |

**Валидация:**
- Если `relative_percent` > 50 — warning «очень крупный эффект, проверь baseline»
- Если `absolute_pp` > baseline — warning «MDE больше baseline, странно»

**YAML:**
```yaml
mde:
  value: <number>
  unit: <unit>
  direction: <increase|decrease|any>  # из Q02
```

**Обязательность:** да

## Вопрос 08 · Доступный трафик

**Формулировка:** «Сколько юзеров в день можно отдать в тест?»  
**Подсказка:** «Это весь трафик, который пойдёт в эксперимент (control + treatment). От этого зависит длительность теста.»

**Тип:** число + выбор юнита (пользователей/сессий).

**Юнит должен совпадать с Q06.** Если не совпадает — warning.

**YAML:**
```yaml
daily_traffic:
  value: <number>
  unit: <user|session|cluster>
```

**Обязательность:** да

## Вопрос 09 · Guardrails

**Формулировка:** «Какие метрики не должны просесть?»  
**Подсказка:** «Метрики, которые мониторим параллельно с главной. Если они нарушаются — тест останавливаем, даже если главная метрика растёт.»

**Тип:** список (можно добавлять/удалять). Каждый элемент:
- Название метрики (текст)
- Колонка в csv (текст, snake_case)
- Направление: `max` (не должна расти) / `min` (не должна падать)
- Порог: число + единица (`%` rel. или абс.)

**Дефолтные предложения** (можно принять/отклонить):
- `bounce_rate` max +5% rel.
- `time_on_site` min −10% rel.

**Валидация:**
- Хотя бы 1 guardrail — иначе warning при скоринге (но переход разрешён)
- Имя guardrail не должно совпадать с main metric

**YAML:**
```yaml
guardrails:
  - name: <text>
    column: <snake_case>
    direction: <max|min>
    threshold:
      value: <number>
      unit: <relative_percent|absolute>
```

**Обязательность:** мягкая (можно оставить пустым, но скоринг занизится)

## Вопрос 10 · Stop conditions и Decision rules

Объединяю два логически связанных вопроса в одну форму, потому что они тесно связаны.

**Формулировка:** «Когда останавливаем тест и как принимаем решение?»

**Stop conditions** — чек-боксы с дефолтами:
- ☑ SRM detected (chi² p < 0.001) — дефолт включён
- ☑ Guardrail breach > 24h — дефолт включён
- ☑ Length cap: __ дней — дефолт включён, значение = вычисленная длительность × 2
- ☐ Manual stop — опционально

**Decision rules** — три текстовых поля с дефолтами:
- **SHIP** (дефолт): «CI не пересекает 0 и нижняя граница ≥ {MDE/2} rel.»
- **ITERATE** (дефолт): «ns но direction positive в 2+ сегментах»
- **KILL** (дефолт): «guardrail breach или CI ≤ −{MDE/2} rel.»

Дефолты подставляются с подстановкой реального MDE из Q07.

**YAML:**
```yaml
stop_conditions:
  - srm_detected
  - guardrail_breach_24h
  - length_cap_days: <number>
decision_rules:
  ship: <text>
  iterate: <text>
  kill: <text>
```

**Обязательность:** мягкая (дефолты заполнят всё)

## Опциональный шаг · Data Peek

**После 10 вопросов** показываем экран с предложением загрузить csv для проверки данных.

**Формулировка:** «Загрузи csv с историческими данными по метрике — посчитаем реальный baseline и проверим распределение»  
**Подсказка:** «Опционально. Без этого скор тест-плана будет ниже, но не критично.»

**Что просим:** csv с минимум двумя колонками:
- `metric_column` (та, что задана в Q04)
- опционально `date` или `timestamp` для проверки стабильности

**Что считаем на клиенте:**
- Реальный baseline (среднее по колонке метрики)
- Описательная статистика (min, max, std, медиана)
- Распределение (гистограмма)
- Если есть `date` — стабильность по дням (CV)

**Что показываем:**
- Сравнение «введённый baseline (Q05)» vs «реальный baseline»
- Если расходятся > 20% — предлагаем обновить
- Гистограмма
- График стабильности по дням

**YAML:**
```yaml
data_peek:
  uploaded: <true|false>
  filename: <text>
  rows: <number>
  baseline_computed: <number>
  std_computed: <number>           # σ метрики, нужно для t-test sample size
  baseline_match_user_input: <true|false>
  distribution_check: <ok|skewed|bimodal|other>
  stability_cv: <number>
```

**Обязательность:** нет, но влияет на скоринг (см. SCORING.md, группа 4).

## Продвинутые параметры (скрытая секция)

Доступна через ссылку «Продвинутые параметры» на любом шаге. Если пользователь её не открывает — используются дефолты.

| Параметр | Дефолт | YAML |
|----------|--------|------|
| α (уровень значимости) | 0.05 | `alpha: 0.05` |
| Power (мощность) | 0.80 | `power: 0.80` |
| Двусторонний тест | true | `two_sided: true` |
| Variance reduction | null | `variance_reduction: null \| cuped` |
| Стратификация | null | `stratification_by: null \| <field>` |
| Holdback после ship | null | `holdback_percent: null \| <number>` |

## Карта вопросов в UI

Сбоку от формы показываем кликабельный список:

```
КАРТА ВОПРОСОВ

01 ✓ Цель теста                    [product_change]
02 ✓ Гипотеза                       [4/4 слотов заполнены]
03 ✓ Тип метрики                    [proportion]
04 ✓ Имя метрики                    [cr_to_partner_click]
05 ✓ Baseline                       [3.1%]
06 ✓ Единица рандомизации           [user]
07 ✓ MDE                            [8% rel.]
08 ✓ Трафик в день                  [42 000 user]
09 → Guardrails                     [2 метрики]
10   Stop & Decision rules          [—]

+    Data peek (опционально)        [не загружено]
```

**Поведение:**
- Клик по любому пункту → переход к этому вопросу
- Расхлопывание (▼) → показывает текущий ответ inline без перехода
- Текущий вопрос помечен стрелкой `→`
- Отвеченные — галочкой `✓`

## Маппинг вопросов в итоговый test_plan.md

| Вопрос | YAML frontmatter | Markdown секция |
|--------|------------------|-----------------|
| Q01 | `goal_type` | (в Notes если other) |
| Q02 | `hypothesis.slots` | `## Hypothesis` (текст) |
| Q03 | `metric_type` | — |
| Q03.1 | `ratio_components` | — |
| Q04 | `metric_name`, `metric_column` | (в заголовке) |
| Q05 | `baseline` | — |
| Q06 | `randomization_unit` | — |
| Q06.1 | `cluster_field` | — |
| Q07 | `mde` | — |
| Q08 | `daily_traffic` | — |
| Q09 | `guardrails` | `## Guardrails` (список) |
| Q10 | `stop_conditions`, `decision_rules` | `## Stop conditions`, `## Decision rules` |
| Data peek | `data_peek` | — |
| Продвинутые | `alpha`, `power`, etc | — |

Поля, которые **вычисляются**, а не запрашиваются:
- `test_method` — выбирается автоматически из `metric_type` (см. матрицу в SCORING.md). Если есть несколько подходящих — берётся первый.
- `sample_size_per_arm` — вычисляется из `baseline`, `mde`, `alpha`, `power` формулой.
- `duration_days` — `sample_size_per_arm * 2 / daily_traffic`, округление вверх.

Эти поля показываются пользователю как «рассчитано» и могут быть переопределены в продвинутых параметрах.
