# Notebook Templates

## Принципы

1. **Ноутбук — это валидный JSON.** Никакой ipynb-магии, просто склейка ячеек по схеме nbformat 4.
2. **Каждая ячейка — отдельный JSON-шаблон** с плейсхолдерами. Плейсхолдеры подставляются из `state.brief` при сборке.
3. **Ячейки самодостаточны.** Каждая ячейка может содержать свои импорты, чтобы пользователь мог запускать их по отдельности и понимать, что делает.
4. **Минимум зависимостей.** pandas, numpy, scipy, statsmodels, matplotlib. Никакого экзотического.
5. **Понятные комментарии.** Каждая ячейка начинается с markdown-блока, объясняющего, что и зачем.

## Структура шаблона ячейки

`templates/notebook/02-srm.ipynb.json`:

```json
{
  "id": "srm_check",
  "name": "Sample Ratio Mismatch",
  "description": "Проверка, что размеры групп распределены ожидаемо",
  "default_enabled": true,
  "requires": ["load"],
  "cells": [
    {
      "cell_type": "markdown",
      "source": [
        "## SRM Check\n",
        "Sample Ratio Mismatch проверяет, что фактическое соотношение размеров групп ",
        "соответствует ожидаемому (обычно 50/50). Значимое отклонение указывает на ",
        "техническую проблему в рандомизации, и результаты теста нельзя доверять.\n"
      ]
    },
    {
      "cell_type": "code",
      "source": [
        "from scipy.stats import chisquare\n",
        "\n",
        "group_sizes = df['variant'].value_counts()\n",
        "expected = [len(df) / 2, len(df) / 2]\n",
        "chi2, p = chisquare(group_sizes, f_exp=expected)\n",
        "\n",
        "print(f'Group sizes: {dict(group_sizes)}')\n",
        "print(f'Chi² = {chi2:.4f}, p = {p:.4f}')\n",
        "\n",
        "if p < 0.001:\n",
        "    print('⚠ SRM DETECTED — STOP, investigate randomization')\n",
        "else:\n",
        "    print('✓ No SRM detected')"
      ]
    }
  ]
}
```

## Сборка финального .ipynb

Алгоритм `notebook-builder.js`:

```javascript
function buildNotebook(state) {
  const enabled = state.notebook_config.cells_enabled;
  const templates = enabled.map(id => loadTemplate(id));
  
  // Проверяем зависимости (если выбран SRM — должен быть Load)
  templates.forEach(t => {
    t.requires.forEach(dep => {
      if (!enabled.includes(dep)) {
        throw new Error(`${t.id} requires ${dep}`);
      }
    });
  });
  
  // Собираем ячейки
  const allCells = [];
  
  // Первая ячейка — header с YAML metadata теста
  allCells.push(buildHeaderCell(state));
  
  // Затем все выбранные шаблоны
  templates.forEach(t => {
    t.cells.forEach(cell => {
      const processed = substitutePlaceholders(cell, state);
      allCells.push(processed);
    });
  });
  
  return {
    nbformat: 4,
    nbformat_minor: 5,
    metadata: {
      kernelspec: { name: "python3", display_name: "Python 3" },
      language_info: { name: "python" },
      statplan: { test_id: state.test_id, version: "0.1" }
    },
    cells: allCells
  };
}
```

## Плейсхолдеры в шаблонах

Ячейки могут содержать переменные вида `{{var}}`, которые подставляются из state:

| Плейсхолдер | Источник | Пример значения |
|-------------|----------|-----------------|
| `{{test_id}}` | `state.test_id` | `bm-main-cta-v2` |
| `{{metric_name}}` | `state.brief.metric_name` | `cr_to_partner_click` |
| `{{metric_column}}` | `state.brief.metric_column` | `converted` |
| `{{baseline}}` | `state.brief.baseline` | `0.031` |
| `{{mde_value}}` | `state.brief.mde.value` | `8` |
| `{{alpha}}` | `state.brief.alpha` | `0.05` |
| `{{power}}` | `state.brief.power` | `0.80` |
| `{{guardrail_columns}}` | `state.brief.guardrails[].name` | `["bounce_rate", "time_on_site"]` |
| `{{randomization_unit_column}}` | `state.brief.randomization_unit` | `user_id` |

## Каталог ячеек (v0)

| ID | Название | Обязательная | Зависит от | Применима когда |
|----|----------|--------------|------------|-----------------|
| `load` | Загрузка данных + EDA | ✓ | — | всегда |
| `srm` | Sample Ratio Mismatch | ✓ | load | всегда |
| `balance` | Баланс по сегментам | ✓ | load | всегда |
| `novelty` | Novelty effect | ✓ | load | если duration_days ≥ 3 |
| `main_test` | Основной тест + CI | ✓ | load | всегда |
| `guardrails` | Проверка guardrails | ✓ | load | если есть guardrails |
| `segments` | Сегментный анализ | — | main_test | опционально |
| `bootstrap_ci` | Bootstrap CI | — | main_test | для ratio/непараметрических |
| `cuped` | CUPED variance reduction | — | load | если есть pre-period данные |
| `delta_method` | Delta method для ratio | — | load | если metric_type=ratio |

## Header-ячейка ноутбука

Первая ячейка каждого ноутбука — markdown-блок с шапкой теста:

```markdown
# Analysis: {{test_id}}

> Generated by stat·plan on {{date}}.  
> Test plan: see attached test_plan.md.

## Test parameters
- Metric: `{{metric_name}}` ({{metric_type}})
- Method: `{{test_method}}`
- Sample size per arm: {{sample_size_per_arm}}
- Duration: {{duration_days}} days
- α = {{alpha}}, power = {{power}}
- MDE: {{mde_value}}{{mde_unit}}

## Decision rules
{{decision_rules_text}}

---

**To run this notebook:**
1. Place your `experiment_results.csv` next to this file
2. Run all cells from top to bottom
3. Review warnings and decision-rule check at the end
```

## Адаптация шаблонов под бриф

Некоторые ячейки имеют несколько вариаций кода в зависимости от ответов брифа:

**Например, `main_test`** имеет 4 варианта реализации в зависимости от `test_method`:
- `z_test_proportions` → `statsmodels.stats.proportion.proportions_ztest`
- `t_test` → `scipy.stats.ttest_ind`
- `welch_t_test` → `scipy.stats.ttest_ind(..., equal_var=False)`
- `bootstrap` → ручная реализация bootstrap-CI

Файлы шаблонов в этом случае:
```
templates/notebook/main_test/
├── _meta.json         # общие метаданные ячейки
├── z_test.cells.json  # вариант для proportion
├── t_test.cells.json
├── welch.cells.json
└── bootstrap.cells.json
```

`notebook-builder.js` выбирает нужный вариант по `state.brief.test_method`.

## Что НЕ кладём в ноутбук v1

- Sequential testing / mSPRT (хорошая идея для v2)
- Heterogeneous treatment effects через ML (causal forests etc) — слишком тяжело
- Power retrospective analysis
- Полноценный CUPED — добавим опционально, но честно пометим как experimental

## Проверка валидности

Перед скачиванием:
1. Прогоняем сгенерированный JSON через JSON-валидатор
2. Проверяем, что все плейсхолдеры подставлены (нет `{{...}}` в финальном тексте)
3. Имя файла: `{test_id}_analysis.ipynb`

## Схема данных, которую ожидает ноутбук

Сгенерированный ноутбук обращается к колонкам csv по строго определённым именам. Список колонок **динамический** — зависит от конфигурации плана и от того, какие ячейки включены в конструкторе.

### Обязательные колонки (всегда)

| Колонка | Тип | Источник | Описание |
|---------|-----|----------|----------|
| `variant` | string | фиксированно | Значения `control` или `treatment` |
| `{metric_column}` | number / int | `state.brief.metric_column` | Значение метрики на единицу анализа |
| `{randomization_unit}_id` | string / int | `state.brief.randomization_unit` | `user_id`, `session_id` или `cluster_id` |

### Условно-обязательные колонки

Появляются в схеме, если включена соответствующая ячейка:

| Колонка | Тип | Когда нужна | Используется в ячейке |
|---------|-----|-------------|----------------------|
| `day` или `date` | int / date | Включён `novelty_effect` | Сравнение эффекта дни 1-2 vs 3-5 |
| `{guardrail.column}` для каждого guardrail | number | Есть guardrails в плане | Ячейка `guardrails_check` |
| `{segment_field}` | string | Включён `segments` | Сегментный анализ (например, `geo`, `user_type`) |
| `{cluster_field}` | string | `randomization_unit == cluster` | Group-by в SRM и balance check |
| `{pre_period_metric}` | number | Включён `cuped` | CUPED variance reduction |

### Как генерируется секция в ноутбуке

Header-ячейка ноутбука (первая markdown-ячейка) содержит явный список ожидаемых колонок:

```markdown
## Expected CSV schema

This notebook expects `experiment_results.csv` with the following columns:

| Column | Type | Required | Description |
|--------|------|----------|-------------|
| `user_id` | int/string | ✓ | Randomization unit identifier |
| `variant` | string | ✓ | "control" or "treatment" |
| `converted` | int (0/1) | ✓ | Main metric (proportion) |
| `bounce_rate` | float | ✓ | Guardrail metric |
| `time_on_site` | float | ✓ | Guardrail metric |
| `day` | int (1-N) | ✓ | Day number for novelty check |
| `geo` | string | optional | For segment analysis (if enabled) |

If your csv is missing required columns — the cell using that column will fail. Optional columns
can be missing — corresponding analyses will be skipped with a warning.
```

Этот список строится на клиенте при генерации `.ipynb` из шаблонов ячеек и подставляется в header-ячейку.

### Связь со схемой demo-csv

Demo-csv (4 базовых файла под `metric_type`) спроектированы так, чтобы покрывать **базовую схему + типичные guardrails + day + geo**. То есть для дефолтной конфигурации ноутбука demo-csv подходит сразу.

**Когда demo-csv не подходит:**
- Если пользователь поменял `metric_column` (имя отличается от того, что в demo) — нужно либо переименовать колонку в csv, либо в коде ноутбука
- Если включена ячейка `cuped` — demo-csv не содержит pre-period колонок, ячейка будет пропущена
- Если включена ячейка `segments` с нестандартным сегментом — demo-csv содержит только `geo`

Эти ограничения отображаются на шаге 3 (конструктор) рядом с кнопкой скачивания demo-csv как inline-warnings.

### Отображение схемы в UI конструктора

На шаге 3 (конструктор) в блоке Demo CSV показываем таблицу схемы. Это даёт пользователю понять:
1. Какие колонки должны быть в его реальном csv (когда он будет грузить на шаге 4)
2. Что именно содержит demo-csv (для проверки ноутбука)

Схема обновляется реактивно при изменении toggle-ов ячеек в конструкторе — включил `segments` → в схеме появилась строчка про segment column.
