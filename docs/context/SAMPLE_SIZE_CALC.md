# Sample Size Calculation

Формулы расчёта размера выборки `sample_size_per_arm` и длительности `duration_days` для разных комбинаций `metric_type × test_method`. Все формулы реализуются на клиенте в `assets/brief/calculator.js`.

## Зачем нужно

На этапе брифа (после Q05 baseline + Q07 MDE + Q08 traffic) пользователю показывается расчётное «sample size / arm: ~38 400, длительность: ~5 дней». Это критично:
- Пользователь видит, реалистичен ли тест (5 дней vs 6 недель — большая разница)
- Если sample size недостижим — пользователь может пересмотреть MDE или метод
- При выборе test_method в продвинутых параметрах sample size пересчитывается

Расчёт **выполняется реактивно** при изменении любого из полей: baseline, MDE, alpha, power, daily_traffic, test_method.

## Общая модель

Размер выборки = функция от:
- `α` — уровень значимости (обычно 0.05)
- `power` — мощность теста (обычно 0.80), то есть `1 - β`
- `δ` — величина эффекта в единицах метрики (вычисляется из MDE и baseline)
- `σ²` — дисперсия метрики (или её аналог в зависимости от типа)
- односторонний/двусторонний тест (по умолчанию двусторонний)

Длительность теста:
```
duration_days = ceil(sample_size_per_arm * 2 / daily_traffic)
```

То есть нужно `N × 2` юзеров (на обе группы), при трафике `daily_traffic` юзеров в день получается столько-то дней. Округление вверх.

## Случай 1. Z-test для пропорций (proportion)

Основной случай для конверсий. Реализуется первым.

### Формула

Нужно сравнить две пропорции `p₁` и `p₂` с гипотезой `H₀: p₁ = p₂`:

```
p₁ = baseline                           (контрольная конверсия)
p₂ = p₁ * (1 + MDE_relative)            (если MDE в относительных %)
   = p₁ + MDE_absolute                  (если MDE в абсолютных п.п.)
δ  = p₂ - p₁                            (абсолютная разница)
p̄  = (p₁ + p₂) / 2                      (объединённая пропорция)

n_per_arm = ((z_α/2 * sqrt(2 * p̄ * (1 - p̄)) + z_β * sqrt(p₁ * (1 - p₁) + p₂ * (1 - p₂))) / δ)²
```

Где:
- `z_α/2 = Φ⁻¹(1 - α/2)` — квантиль стандартного нормального распределения
- `z_β = Φ⁻¹(power)` — квантиль для мощности

### Что подставляем из брифа

| Параметр | YAML-путь | Дефолт |
|----------|-----------|--------|
| `p₁` | `state.brief.baseline.value` | — (обязательно) |
| MDE rel/abs | `state.brief.mde` | — (обязательно) |
| `α` | `state.brief.alpha` | 0.05 |
| `power` | `state.brief.power` | 0.80 |
| two-sided | `state.brief.two_sided` | true |

Если `two_sided = false` — заменяем `z_α/2` на `z_α`.

### Пример (для проверки реализации)

```
p₁ = 0.031, MDE = +8% rel., α = 0.05, power = 0.80, two_sided

p₂  = 0.031 * 1.08 = 0.03348
δ   = 0.00248
p̄   = 0.03224

z_α/2 = 1.95996
z_β   = 0.84162

n = ((1.95996 * sqrt(2 * 0.03224 * 0.96776) + 0.84162 * sqrt(0.031 * 0.969 + 0.03348 * 0.96652)) / 0.00248)²
  ≈ ((1.95996 * 0.25195 + 0.84162 * 0.25199) / 0.00248)²
  ≈ ((0.49381 + 0.21208) / 0.00248)²
  ≈ (284.63)²
  ≈ 81 014
```

То есть **n ≈ 81 014 на arm** для этого MDE. Если в брифе пользователь указал MDE = 8%, мы покажем именно это число. Заметь, в мокапах я писал «38 400» — это была упрощённая оценка, реальная формула даёт большее число для таких маленьких baseline.

**Замечание про мокап:** значение `38 400` в мокапах использовалось как иллюстрация — оно ближе к расчёту для MDE 12% или для baseline 5%. При реализации нужно сверить: пересчитать пример выше при разных параметрах и убедиться, что цифры в UI соответствуют формуле.

## Случай 2. T-test для непрерывных метрик (continuous, равные дисперсии)

### Формула

```
δ = размер эффекта в единицах метрики
σ = стандартное отклонение метрики (одинаковое для обеих групп)

n_per_arm = 2 * ((z_α/2 + z_β) * σ / δ)²
```

В каноничном варианте используется `t_α/2,df` (t-распределение), но для больших выборок разница с нормальным минимальна. Для простоты в v1 используем нормальное приближение. Для маленьких выборок (< 100) можно показать предупреждение «расчёт приближённый, проконсультируйся с аналитиком».

### Источник σ

Согласно нашему решению:

1. **Если data peek выполнен** (`state.brief.data_peek.uploaded == true`) → берём σ из загруженного csv
2. **Если data peek не выполнен** → используем fallback: `CV = 1`, то есть `σ = baseline.value`. Показываем warning рядом с расчётом:
   > ⚠ σ метрики неизвестна, использован fallback (CV=1). Расчёт приближённый, загрузи csv в Data Peek для точного значения.

### Что подставляем из брифа

| Параметр | Источник | Дефолт |
|----------|----------|--------|
| `δ` | вычисляется из `baseline.value` и `mde` | — |
| `σ` | `state.brief.data_peek.std_computed` или fallback `baseline.value` | fallback |
| `α`, `power`, two-sided | из брифа | как выше |

### Пример

```
baseline = 100₽ (ARPU), MDE = +5% rel., σ = 80₽ (из data peek)

δ = 100 * 0.05 = 5
n = 2 * ((1.95996 + 0.84162) * 80 / 5)²
  = 2 * (2.80158 * 16)²
  = 2 * (44.825)²
  = 2 * 2009.3
  ≈ 4 019
```

## Случай 3. Welch t-test (continuous, неравные дисперсии)

По-хорошему — дефолт для continuous-метрик, потому что эффект может изменить не только среднее, но и дисперсию.

### Формула

Если мы предполагаем, что `σ₁` (control) и `σ₂` (treatment) могут отличаться — формула усложняется. На этапе планирования у нас одна σ (из data peek), поэтому **в v1 для расчёта sample size Welch == обычный t-test**.

Различие появится только при реальном анализе данных (ноутбук использует Welch, если включён в test_method), но для prospective sample size это одна и та же формула.

```
n_per_arm_welch == n_per_arm_t_test
```

Так и помечаем в коде. Это нормально — если бы у нас были разные σ для control и treatment на этапе планирования, мы бы их откуда-то знали, что нереалистично.

## Случай 4. Mann-Whitney (непараметрический)

### Подход

Закрытой формулы для prospective sample size нет (зависит от формы распределения). Используем **приближение через t-test с поправкой на эффективность**:

```
n_per_arm_mw = n_per_arm_t_test / asymptotic_relative_efficiency
```

Asymptotic Relative Efficiency (ARE) для MW vs t-test:
- При нормальном распределении: ARE = `3/π ≈ 0.955`
- При тяжёлых хвостах: ARE может быть > 1 (MW требует меньше выборки)
- При неизвестном распределении: используем **0.864** как консервативное значение (для двойного экспоненциального распределения)

```
n_per_arm_mw = ceil(n_per_arm_t_test / 0.864) ≈ n_per_arm_t_test * 1.157
```

То есть **MW требует примерно на 15% больше выборки**, чем t-test, в общем случае.

### Что показываем пользователю

> Расчёт для MW — приближение. Фактический размер выборки может отличаться на ±15% в зависимости от формы распределения. Если данные близки к нормальному распределению — переключись на t-test.

## Случай 5. Bootstrap

### Подход

Аналогично MW, нет закрытой формулы. В v1 используем **то же значение, что и для t-test**, с warning:

```
n_per_arm_bootstrap = n_per_arm_t_test
```

С пометкой:
> Bootstrap — гибкий, но непредсказуемый по требуемой выборке. Расчёт ориентировочный. Для точной оценки сделай pilot и проверь стабильность bootstrap-CI.

### Почему не симулируем

Симуляция bootstrap для разных N в браузере — медленная и требует знания распределения метрики. Если у пользователя есть data peek — можно использовать его данные для bootstrap-симуляции, но это уже task для v2.

## Случай 6. Delta method для ratio-метрик

### Зачем

Ratio-метрики (CTR на сессию, conversion rate на сессию когда юнит-рандомизации — user) — числитель и знаменатель из разных юнитов. Простой t-test даёт смещённую дисперсию.

### Формула

Метрика `R = X / Y`, где `X` — сумма числителя на пользователя (например, количество кликов), `Y` — сумма знаменателя на пользователя (количество сессий).

Дисперсия R через дельта-метод:

```
Var(R) ≈ (1/μ_Y²) * Var(X) + (μ_X² / μ_Y⁴) * Var(Y) - 2 * (μ_X / μ_Y³) * Cov(X, Y)
```

Где `μ_X, μ_Y` — средние, `Var(X), Var(Y)` — дисперсии на пользователя, `Cov(X, Y)` — ковариация.

Sample size после этого:

```
n_per_arm = 2 * ((z_α/2 + z_β) * sqrt(Var(R)) / δ)²
```

где `δ` — ожидаемое изменение в R.

### Источник Var(R)

Только из data peek. **Если data peek не выполнен — расчёт невозможен.** Показываем пользователю:

> Для ratio-метрик нужен data peek с числителем и знаменателем. Загрузи csv в шаге Data Peek с колонками `numerator_per_user` и `denominator_per_user`.

В v1 это нормально — ratio-метрики реже встречаются у новичков, кому в первую очередь нужен тул.

## Случай 7. Кластерная рандомизация

### Поправка на design effect

Если рандомизация на уровне кластеров (geo, домохозяйство), а единица анализа — user, sample size увеличивается:

```
DE = 1 + (m - 1) * ICC
n_clustered = n_simple * DE
```

Где:
- `m` — средний размер кластера (юзеров на кластер)
- `ICC` — intraclass correlation (внутрикластерная корреляция метрики)

### Проблема

`ICC` пользователь почти никогда не знает. Без data peek — расчёт пальцем в небо.

### Что делаем

1. **Если data peek есть и в csv есть колонка кластера** — считаем ICC из данных, применяем design effect
2. **Если нет** — показываем sample size как для simple randomization с warning:
   > Кластерная рандомизация требует увеличения выборки. ICC неизвестен, расчёт приближённый. Реальная выборка может быть в 1.5–5 раз больше. Сделай data peek с колонкой кластера для точного расчёта.

## Edge cases и валидация

| Условие | Что показываем |
|---------|----------------|
| `baseline = 0` или `baseline = 1` для proportion | "Baseline 0 или 100% — тест бессмыслен. Проверь значение." |
| Вычисленное `n > 10_000_000` | "Расчётная выборка > 10M, тест нереалистичен. Увеличь MDE или пересмотри метрику." |
| Вычисленное `n < 30` | "Расчётная выборка < 30, маловато для асимптотических методов. Используй точные тесты или увеличь power." |
| `daily_traffic` не задан | Показываем sample size, длительность пишем "—". |
| Длительность > 90 дней | Warning: "Тест займёт >3 месяцев — нереалистично. Пересмотри параметры." |
| `MDE > baseline * 2` (для proportion) | Warning: "MDE больше чем baseline — необычно. Проверь единицы." |

Готовые реализации этих функций есть в библиотеке [simple-statistics](https://simplestatistics.org/) (`ss.probit`, `ss.cumulativeStdNormalProbability`). Можем взять оттуда или написать самим (10-15 строк).

### Структура модуля

```javascript
// assets/brief/calculator.js

export function calculateSampleSize(brief) {
  const { metric_type, test_method } = brief;

  switch (test_method) {
    case 'z_test_proportions':
      return zTestProportions(brief);
    case 't_test':
    case 'welch_t_test':
      return tTest(brief);
    case 'mannwhitney':
      return tTest(brief, { areCoefficient: 0.864 });
    case 'bootstrap':
      return tTest(brief, { warning: 'bootstrap_approximate' });
    case 'delta_method':
      return deltaMethod(brief);
    default:
      throw new Error(`Unknown test method: ${test_method}`);
  }
}

export function calculateDuration(sampleSizePerArm, dailyTraffic) {
  if (!dailyTraffic) return null;
  return Math.ceil((sampleSizePerArm * 2) / dailyTraffic);
}
```

Каждая под-функция возвращает объект:

```javascript
{
  sample_size_per_arm: number,
  duration_days: number | null,
  warnings: string[],   // массив предупреждений из edge cases
  computed_from: 'formula' | 'approximation' | 'fallback'
}
```

## Что НЕ покрываем в v1

- **Sequential testing** (mSPRT, always-valid CI) — отдельная история, v2
- **Adaptive sample size** — пересчёт по ходу теста, v2
- **Stratified sample size** — теоретически уменьшает N, но требует знания дисперсий по стратам
- **CUPED-adjusted sample size** — `n_cuped = n * (1 - ρ²)`, где ρ — корреляция метрики с pre-period covariate. Можно добавить в v1 как опцию в продвинутых параметрах, но требует data peek с pre-period колонкой.

CUPED — хороший кандидат на добавление сразу, потому что он реально снижает требуемую выборку на 20-50%. Решим по результатам v1.
