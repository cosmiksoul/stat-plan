# User Flow

## Обзор

Пять шагов с развилкой на старте. Между шагами — артефакты (md / ipynb / csv), которые можно скачать и загрузить обратно.

```
[Старт: выбор пути]
   ├─→ Начать с брифа: [1. Бриф] → [2. Тест-план] → [3. Конструктор] → [4. Быстрая валидация] → [5. Скачать артефакты]
   └─→ Загрузить план: ───────────→ [2. Тест-план] → [3. Конструктор] → [4. Быстрая валидация] → [5. Скачать артефакты]
```

Пользователь может вернуться на любой предыдущий шаг и переделать. Состояние сохраняется в localStorage.

---

## Стартовый экран

**Цель.** Дать пользователю выбрать, начинать ли заполнение брифа с нуля или продолжить с уже готового тест-плана.

**Что видит пользователь.**
- Хедлайн и краткое описание тула
- Две большие карточки с вариантами:
  - **«Начать с брифа»** — обычный путь для новых пользователей
  - **«У меня уже есть план»** — drag-and-drop зона для `test_plan.md`
- Кнопка `? Включить тур` в шапке — переключает тур-плашки на всех шагах

**Поведение.**
- Клик по «Начать с брифа» → state.started = true, переход на шаг 1
- Загрузка `test_plan.md` во вторую карточку:
  1. Парсим YAML frontmatter и markdown-секции
  2. Заполняем state.brief и state.plan из распарсенных данных
  3. state.plan.status = approved (план уже готов)
  4. Переход на шаг 3 (конструктор)
- Если файл невалидный — показываем понятную ошибку с описанием, что не так в формате

**Под капотом.**
- Стартовый экран показывается, пока `state.started == false`
- Степпер сверху НЕ отображается на стартовом экране
- Если пользователь жмёт «Новый тест» на финальном шаге — state очищается, возвращаемся сюда

## Тур-режим

**Цель.** Помочь новому пользователю понять, что происходит на каждом шаге.

**Как включается.**
- Кнопка `? Включить тур` в шапке — переключает `body.tour = true/false`
- Состояние тура — глобальное для сессии, сохраняется в localStorage
- Закрывается через кнопку `✕ Закрыть тур` в той же шапке (одним кликом, не по плашке за плашкой)

**Что меняется в UI.**
- На стартовом экране и на каждом шаге появляется tour-плашка сверху
- Плашка объясняет, что происходит на этом экране, на что обратить внимание
- Никаких оверлеев, подсветок элементов, обязательных переходов — пользователь сам кликает куда хочет

**Связь с demo-csv.**
- Тур и demo-csv — это разные вещи. Тур — пояснения. Demo-csv — тестовые данные для ноутбука.
- Demo-csv доступен в конструкторе (шаг 3) независимо от того, включён ли тур.

## Шаг 1. Бриф

**Цель.** Собрать всю информацию, необходимую для построения тест-плана.

**Что видит пользователь.**
- Прогресс-бар сверху: `N / M вопросов`
- Один-два вопроса на экран, идущих линейно
- Сбоку — карта всех вопросов с отметками о пройденных
- Кнопки `← Назад` / `Дальше →`

**Что под капотом.**
- Вопросы заданы в `questions.js` как дерево с ветвлениями (см. дерево в `OPEN_QUESTIONS.md` — оно ещё в проработке)
- Каждый ответ обновляет `state.brief`
- Часть вопросов раскрывает дополнительные на основе ответов (выбрал `ratio metric` → появляется вопрос про дельта-метод)
- Прогресс рассчитывается от количества обязательных вопросов, а не от всех возможных

**Особый случай — гипотеза.**
Гипотеза вводится как свободный текст по шаблону:
> Если **[ изменение ]**, то **[ метрика ]** **[ направление ]** на **[ Δ ]**, потому что **[ механизм ]**.

Тул проверяет наличие 4 структурных слотов. **Не оценивает «качество идеи»** — только проверяет, что все слоты заполнены. Эвристики для определения слотов:
- `изменение` — текст после «если» до запятой/«то»
- `метрика` — текст после «то» до глагола направления
- `направление + Δ` — наличие глагола (вырастет/упадёт/изменится) и числа с %
- `механизм` — текст после «потому что»

Если эвристика не находит слот — помечаем как незаполненный, но не блокируем переход дальше.

**Опциональный последний шаг — Data Peek.**
Пользователь может загрузить csv с историческими данными по метрике. Мы:
- Парсим в браузере
- Считаем реальный baseline и базовую описательную статистику
- Сравниваем с тем, что пользователь указал
- Если расходимся — корректируем `state.brief.baseline` и предлагаем пересмотреть MDE

Это опционально и не блокирует переход. Если пользователь не загрузил — просто `data_peek.uploaded = false`.

**Выход.** `state.brief` заполнен → переход к шагу 2.

## Шаг 2. Тест-план

**Цель.** Показать сгенерированный тест-план, дать оценку, дать возможность отредактировать снаружи. Утвердить план перед переходом к сборке ноутбука.

**Что видит пользователь.**

Слева — preview сгенерированного `test_plan.md` с YAML frontmatter и секциями.

Справа — карточка оценки тест-плана: общий скор X/100 + разбивка по 4 группам критериев с конкретными замечаниями.

Кнопки:
- `↓ Скачать test_plan.md` — забрать план для обсуждения с аналитиком (доступно всегда)
- `↑ Загрузить отредактированный test_plan.md` — загрузить версию после правок (доступно в статусе draft)
- `✓ Утвердить план` — финализировать, перейти к конструктору ноутбука (доступно в статусе draft)

**Статусы плана.**

| Статус | Что значит | Что разрешено |
|--------|------------|---------------|
| `draft` | Черновик, можно править | Скачать, загрузить, утвердить |
| `approved` | Утверждён, заморожен | Скачать. Чтобы изменить — нажать «Вернуть в черновик» |

В статусе `approved`:
- План отображается с пометкой «Утверждён»
- Поля брифа на шаге 1 — readonly (можно посмотреть, нельзя изменить)
- Появляется кнопка `↻ Вернуть в черновик` с предупреждением «конфигурация ноутбука будет сброшена»

**Под капотом — генерация md.**
Используется шаблон `test_plan.md.tmpl` с плейсхолдерами. Подставляются значения из `state.brief` и `state.plan.derived`. YAML frontmatter содержит все ключевые параметры в машинно-читаемом виде, включая `status: draft | approved`.

**Под капотом — оценка.**
См. [SCORING.md](SCORING.md). Скор пересчитывается каждый раз, когда меняется состояние.

**Под капотом — загрузка отредактированного md.**
Пользователь скачал план, обсудил с аналитиком, поправил руками. Загружает обратно:
1. Парсим YAML frontmatter → `state.brief` и `state.plan.derived` обновляются
2. Парсим секции `## Hypothesis`, `## Guardrails` и т.д.
3. Если что-то не парсится — помечаем поле как `unparseable`, показываем предупреждение
4. Пересчитываем скор
5. Помечаем `state.plan.edited_externally = true`
6. Статус остаётся `draft`

**Под капотом — утверждение.**
1. `state.plan.status = approved`
2. `state.plan.approved_at = timestamp`
3. Бриф (шаг 1) переключается в readonly режим
4. Конструктор ноутбука (шаг 3) разблокируется и предзаполняется на основе плана
5. Переход на шаг 3

**Под капотом — возврат в черновик.**
1. Показываем подтверждение «текущая конфигурация ноутбука будет сброшена, продолжить?»
2. Если ок:
   - `state.plan.status = draft`
   - `state.notebook_config` сбрасывается на дефолты
   - Бриф снова редактируемый

**Выход.** Пользователь утвердил план → переход на шаг 3.

## Шаг 3. Конструктор ноутбука

**Цель.** Собрать `.ipynb` под утверждённую конфигурацию плана. Опционально скачать demo-csv для тестового прогона.

**Что видит пользователь.**

Сверху — карточка с информацией об утверждённом плане: `test_id`, `metric_type`, `test_method`, `sample_size_per_arm`. Это показывает, под что собирается ноутбук.

Слева — список ячеек ноутбука с переключателями. Дефолты включены из плана:
- Обязательные ячейки (load, SRM, balance, main test, guardrails) — включены, нельзя выключить
- Условно-обязательные (novelty) — включены по умолчанию, если `duration_days ≥ 3`
- Опциональные (segments, bootstrap_ci, CUPED, delta_method) — выключены, можно включить вручную

Справа — секция demo-csv:
- Подсказка: «Нужны данные для проверки ноутбука?»
- Селектор/радио-кнопки с базовыми вариантами под `metric_type`:
  - `proportion` — `demo_proportion.csv`
  - `continuous` — `demo_continuous.csv`
  - `ratio` — `demo_ratio.csv`
  - `count` — `demo_count.csv`
- По умолчанию выбран вариант, соответствующий `state.plan.metric_type`
- Краткое описание выбранного csv: размер, колонки, заложенный эффект

Кнопки:
- `↓ Скачать analysis.ipynb` — основная, по центру
- `↓ Скачать demo_{type}.csv` — рядом, опциональная

**Под капотом — генерация ipynb.**
См. [NOTEBOOK_TEMPLATES.md](NOTEBOOK_TEMPLATES.md). Берём JSON-шаблоны выбранных ячеек, склеиваем в один `.ipynb`, подставляем значения из плана (имя метрики, размер выборки, alpha/power).

**Под капотом — demo-csv.**
Это статические файлы в `assets/demo/`. Не генерируем на клиенте. Если активна продвинутая опция (CUPED, стратификация) — показываем warning «demo-csv не содержит pre-period для CUPED, ячейка будет пропущена».

**Состояние плана здесь.**
План остаётся `approved`. Конструктор пишет в `state.notebook_config`, не трогает `state.plan` и `state.brief`.

**Выход.** Пользователь скачал ipynb (опционально + demo-csv), пошёл запускать тест у себя. Возвращается на шаг 4 когда есть результаты.

## Шаг 4. Быстрая валидация

**Цель.** Быстро проверить базовые условия валидности теста (SRM + sanity vs план) и применить decision rules из плана к результатам, которые пользователь принёс из своего ноутбука. **Не делаем independent validation** — concept «пересчитываем сами теми же формулами» приводил бы к circular validation: наш баг в ноутбуке наш же пересчёт не поймал бы (см. ADR-012). Вместо этого даём прозрачные mechanical checks и применение пользовательских правил, оставляя интерпретацию за человеком.

**Что видит пользователь.**

- Краткая шапка с напоминанием «Что мы здесь делаем» + ссылка на methodology раздел («Что мы НЕ делаем — independent validation»).
- **Форма ручного ввода результатов** (основной путь). Пользователь вбивает 7-10 чисел из своего ноутбука: `control_n`, `treatment_n`, `delta_rel`, `p_value`, `ci_lower`, `ci_upper`, `novelty_flag`, `guardrail_breached`. Каждое поле с подсказкой формата и опциональной валидацией диапазона.
- **Опциональный CSV upload как helper** (не валидатор). Если есть `experiment_results.csv` — тул автозаполнит часть полей (counts по variant для SRM, базовый CR/mean) и оставит остальное на ввод. Никакого «независимого пересчёта Δ, p-value, CI» нет.
- **SRM check** — chi² test на размерах групп. Считается из counts (ручной ввод или csv).
- **Sanity check vs план** — простые сравнения: `csv_rows ≈ 2 × sample_size_per_arm` (если csv загружен), `treatment_n + control_n ≈ plan.sample_size_total`, направление эффекта совпадает с `mde.direction`.
- **Применение decision rules** — из `state.brief.decision_rules`, которые пользователь сам записал в брифе (ADR-004). Выходит рекомендация SHIP / ITERATE / KILL с явной trace на конкретное правило. Это не суждение тула — это применение пользовательских правил.
- **Простые визуализации** из ручного ввода: точечный график Δ с CI vs 0, столбики counts по variant, simple guardrails-индикатор. Не для глубокого анализа — для быстрого визуального sanity.
- **`validation.md`** — генерируется из state.results, входит в финальный пакет на шаге 5.

**Под капотом.**
- **SRM:** chi² test на (control_n, treatment_n) vs ожидаемые 50/50 (или из плана если другая пропорция). Самописная формула, ~5 строк.
- **Sanity:** строковые сравнения и арифметика над числами, никаких pandas-в-браузере.
- **Decision rules применение:** parse `decision_rules` string → eval каждого правила против ручного ввода (или csv-derived counts) → SHIP / ITERATE / KILL. Eval — строго детерминированный, никакой динамической компиляции; ограниченный DSL (CI границы, p-value пороги, guardrails breached).
- **CSV (опциональный helper):** papaparse для разбора + `groupby(variant)` для counts. Никаких полных distribution analytics в браузере (это противоречит ADR-001 для тяжёлых вычислений — реальный анализ остаётся в ноутбуке).
- **`validation.md`** — отдельный шаблон с YAML frontmatter (`test_id`, входы ручного ввода, SRM verdict, decision_rules verdict, рекомендация) + markdown с пояснениями.

**Принцип №3 (тул не принимает решений) усилен.**
- Рекомендация SHIP / ITERATE / KILL — это **применение твоих правил из плана**, не суждение тула.
- Поле «Принятое решение» в read-out (Шаг 5) остаётся пустым и заполняется руками.

**Выход.** `state.results` (ручной ввод + SRM verdict + decision_rules verdict + validation.md ready) → переход к шагу 5.

## Шаг 5. Скачать артефакты

**Цель.** Собрать всё в один пакет для отправки в Confluence / Jira / wiki.

**Что видит пользователь.**

Слева — preview `readout.md` с TL;DR, что знаем точно, чего не знаем, follow-up. Поле для решения (SHIP/ITERATE/KILL) — пустое, заполняется руками. Рекомендация из `validation.md` показана отдельно как «применение твоих decision rules» — это не подмена ручному финальному решению (ADR-004).

Справа — список всех артефактов с размерами:
- `test_plan.md`
- `analysis.ipynb`
- `experiment_results.csv` (если был загружен на Шаге 4 как helper)
- `validation.md` (генерируется на Шаге 4)
- `readout.md` (генерируется здесь)

Кнопки:
- `↓ Скачать всё (.zip)`
- `Скопировать markdown-индекс` — кладёт в буфер шапку с ссылками на все файлы для вставки в Confluence

**Под капотом.**
- `readout.md` генерится из шаблона на основе `state.results` (ручной ввод + verdicts с Шага 4) и `state.brief`.
- JSZip собирает все артефакты в архив.
- Имя архива: `{test_id}_{date}.zip`.
- Все файлы связаны общим `test_id` в YAML frontmatter — они склеиваются в логический набор.

**Выход.** Пользователь забирает zip, заливает в свой репозиторий или wiki. Сессия завершена.

## Переходы между шагами

- **Прямой переход** возможен только если предыдущий шаг считается завершённым (есть `state.brief.complete = true` для шага 1, `state.plan.status = approved` для шага 2 и т.д.)
- **Возврат назад** возможен всегда. При изменении на предыдущем шаге — нижние шаги помечаются как `stale` и требуют переподтверждения.
- **Если план в статусе approved** — бриф на шаге 1 readonly, для изменений нужно явно нажать «Вернуть в черновик» на шаге 2.
- **Прямые ссылки** на шаги (хеш-роутинг `#step2`) поддерживаются, но если состояния нет — перекидывает на стартовый экран.

## Demo-CSV

Демо-данные — это **не часть продакшен-флоу**, а инструмент тестирования сгенерированного ноутбука. Нужны для двух целей:
1. Нубы хотят увидеть, что ноутбук вообще работает на каких-то данных, прежде чем подключать продакшен
2. Можно за минуту проверить, что ноутбук собран корректно под выбранную конфигурацию

**Где доступны.**

Только на шаге 3 (конструктор), рядом с кнопкой скачивания ноутбука. В финальный пакет на Шаге 5 demo-csv НЕ включается — там только реальные артефакты теста.

**Какие файлы.**

4 базовых варианта под `metric_type`:

| Файл | metric_type | Размер | Колонки | Заложенный эффект |
|------|-------------|--------|---------|-------------------|
| `demo_proportion.csv` | proportion | ~75k строк | user_id, variant, converted, bounce_rate, time_on_site, geo, day | Δ rel. +9.3% с novelty в первые 2 дня |
| `demo_continuous.csv` | continuous | ~75k строк | user_id, variant, arpu, sessions, geo, day | Δ rel. +6% к среднему ARPU |
| `demo_ratio.csv` | ratio | ~120k строк | session_id, user_id, variant, clicked, geo, day | Δ rel. +7% к CTR |
| `demo_count.csv` | count | ~75k строк | user_id, variant, events_count, geo, day | Δ rel. +12% к среднему числу событий |

**Как генерируются.**

Статические файлы в репозитории `assets/demo/`. Не генерируются на клиенте — это решение для v1, чтобы не тащить генерацию распределений в браузер. Если в будущем понадобится гибкость — можно перейти на runtime-генерацию через Web Worker.

**Ограничения.**

Если в плане использованы продвинутые опции, которым нужны специальные колонки:
- **CUPED** требует pre-period данных — demo-csv их не содержит, ячейка CUPED будет пропущена при запуске
- **Стратификация по полю X** — если такого поля нет в demo-csv, ячейка работает без стратификации

В этих случаях показываем warning рядом с кнопкой скачивания: «Demo-csv не содержит поля для {feature}, ячейка будет пропущена. Это нормально для теста ноутбука, но не для реальных данных.»
