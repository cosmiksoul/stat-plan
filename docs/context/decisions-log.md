# Decisions Log — stat·plan

> Architecture Decision Records. Каждое значимое архитектурное или продуктовое решение фиксируется здесь.
>
> **Кто пишет:** Cowork по результатам обсуждения с пользователем. Самостоятельно — нет.
>
> **Когда писать ADR:** решение долгоживущее (повлияет на множество будущих спринтов), архитектурное (стек, паттерн, ограничение), или продуктовое стратегическое (что НЕ делаем, почему).

---

## Принципы ADR

1. **ADR пишется до реализации**, не после. Если решение принято в фазе CODE REVIEW (что-то всплыло) — фиксируется тогда же, до того как код пойдёт в main.
2. **ADR не отменяется молча.** Если решение пересматривается — новый ADR со статусом, старый помечается `Superseded by ADR-MMM` или `Withdrawn`.
3. **ADR содержит обоснование.** "Так решили" — недостаточно. Должно быть видно почему.
4. **ADR — не догма.** Если по ходу проекта стало понятно, что ADR ошибочный — открыто пересмотреть, не "обходить молча".

## ADR-009 — Sample size: точные формулы где возможно, приближения с warning где нет

**Date:** 2026-05-14
**Status:** Accepted

**Context:**
Для генерации тест-плана нужно рассчитывать `sample_size_per_arm` и `duration_days` на основе ответов пользователя в брифе. Реализация — на клиенте (нет бэкенда). Не все статистические методы имеют закрытую формулу для prospective sample size: для bootstrap и Mann-Whitney классических формул нет, для ratio-метрик через delta method нужна ковариация числителя и знаменателя, которую пользователь не знает. При этом скрывать эту неопределённость от пользователя — обман: цифра «38 400 / arm» создаёт ложное чувство точности.

**Decision:**

1. Реализуем **точные формулы** для случаев, где они существуют:
   - Z-test для пропорций (proportion)
   - T-test и Welch для continuous (Welch для prospective sample size == обычный t-test)
   - Delta method для ratio (если есть data peek с числителем/знаменателем)

2. Для случаев без закрытой формулы используем **приближение от t-test с пометкой о неточности**:
   - Mann-Whitney: `n_t_test * 1.157` (на основе asymptotic relative efficiency 0.864)
   - Bootstrap: `n_t_test` с warning о том, что фактический размер может отличаться

3. Источник σ для continuous-метрик: из data peek (загруженный csv), иначе fallback CV=1 с warning «расчёт приближённый».

4. Edge cases (n > 10M, n < 30, baseline = 0/1, длительность > 90 дней) — явные warning-сообщения для пользователя.

Все формулы и тестовые кейсы — в `SAMPLE_SIZE_CALC.md`.

**Consequences:**
- Пользователь всегда видит честную оценку: либо «точная цифра», либо «приближение, может отличаться на ±15%».
- На реализации нужны JS-функции `normalInv` и `normalCdf` — либо берём из simple-statistics, либо пишем 10-15 строк сами.
- Реальный sample size для proportion с baseline 3.1% и MDE 8% rel. — ~81 000, а не «38 400» как в ранних мокапах. Это требует пересчёта примеров в UI после реализации.
- В тестовом покрытии должны быть unit-тесты на 7 предопределённых кейсов из SAMPLE_SIZE_CALC.md.

**Alternatives considered:**
- **Симуляция bootstrap на клиенте** — отклонено, медленно и требует знания распределения метрики. Кандидат на v2.
- **Использовать Pyodide для scipy.stats** — отклонено, тащить 10MB рантайма ради статистических функций — оверкилл.
- **Не показывать sample size до загрузки data peek** — отклонено, пользователь хочет видеть прикидку сразу, прежде чем грузить данные.

**Related:**
- `SAMPLE_SIZE_CALC.md` — полный документ с формулами и тестовыми кейсами
- ADR-001 (no backend) — обосновывает реализацию на клиенте

## ADR-008 — Тур-плашки без подсветки и без guided overlay

**Date:** 2026-05-14
**Status:** Accepted

**Context:**
Нужно onboarding-решение для нового пользователя. Рассматривались два подхода: классический guided tour с оверлеем (типа intro.js — подсвечивает элементы, ведёт по рельсам через шаги), и более лёгкий вариант — статичные пояснительные плашки сверху на каждом шаге, которые включаются глобально.

Параллельно был отдельный концепт «демо-режим» — предзаполнить бриф фиктивными данными, чтобы пользователь прошёл флоу не вводя ничего. От этого отказались отдельно (см. consequences): предзаполненный бриф путал пользователя — он видел чужие ответы и не мог их поменять, что создавало ощущение, что тул сломан.

**Decision:**

1. Реализуем **тур-плашки без подсветки**: кнопка `? Включить тур` в шапке, при включении на каждом экране сверху появляется голубая плашка с пояснением «что тут происходит и на что смотреть». Закрывается одним кликом по «✕ Закрыть тур» в той же шапке. Состояние тура — глобальное для сессии.

2. **Демо-режим (предзаполненный бриф) отменён.** Пользователь либо заполняет руками, либо загружает готовый план с диска.

3. **Demo-csv остаётся, но как отдельная фича**, не часть тура. Доступен только на шаге конструктора, рядом с кнопкой скачивания ноутбука.

**Consequences:**
- Не нужны зависимости вроде intro.js — реализация в чистом CSS/JS.
- Меньше визуального шума в продакшен-флоу: плашки появляются только если тур включён, не мешают опытным пользователям.
- Пользователь сохраняет агентность — может тыкать куда хочет, тур не блокирует.
- Минус: для совсем новых пользователей нет «interactive demo» — приходится самим заполнять бриф. Решили, что это нормально, потому что 10 вопросов это не очень много.

**Alternatives considered:**
- **Guided tour с intro.js** — отклонено, тяжёлый паттерн, плохо ложится на раскрывающиеся блоки типа карты вопросов, и пользователь хочет щёлкать сам.
- **Демо-режим с предзаполненным брифом** — отклонено, концептуально кривое: пользователь видел чужие ответы в форме без возможности менять.
- **Видео-туториал в шапке** — отклонено, требует поддержки видео, обновления при изменении UI.

**Related:**
- ADR-007 (demo-csv) — связанная фича, отдельная от тура

## ADR-007 — Demo-csv как статические файлы под metric_type

**Date:** 2026-05-14
**Status:** Accepted

**Context:**
Пользователь скачал ноутбук в конструкторе — нужно дать возможность проверить, что ноутбук работает, до подключения продакшен-данных. Рассматривались варианты: runtime-генерация csv на клиенте (Web Worker с биномиальными/нормальными распределениями) и набор статических файлов в репозитории.

Параллельно стоял вопрос множественности: ноутбук генерируется под `metric_type × test_method`, и универсальный demo-csv не подходит — для proportion нужны бинарные значения, для continuous — непрерывные, для ratio — session-level данные с числителем и знаменателем.

**Decision:**

1. **4 статических csv-файла** в `assets/demo/`, по одному на `metric_type`:
   - `demo_proportion.csv` (~75k строк, Δ rel. +9.3%, novelty первые 2 дня)
   - `demo_continuous.csv` (~75k строк, схема для ARPU/времени, Δ rel. +6%)
   - `demo_ratio.csv` (~120k строк, session-level, Δ rel. +7%)
   - `demo_count.csv` (~75k строк, count events, Δ rel. +12%)

2. **На шаге конструктора** выбор demo-csv предзаполняется на основе `state.plan.metric_type`. Пользователь может выбрать другой вариант или вообще не качать.

3. **Demo-csv не входит в финальный read-out zip.** Там только реальные артефакты теста.

4. **Ограничения честно показываются:** если включена ячейка CUPED — demo-csv не содержит pre-period колонок, ячейка будет пропущена. Это отображается inline-warning рядом с кнопкой скачивания.

**Consequences:**
- Простота поддержки: 4 файла в репозитории, никакой генерации в браузере.
- Минус гибкости: если пользователь хочет проверить ноутбук с включённой стратификацией по нестандартному полю — demo-csv не подойдёт. Решили, что это редкий кейс, можно проигнорировать в v1.
- Размер репозитория увеличивается на ~16MB (4 файла × 4MB). Для GitHub Pages это нормально.
- Кандидат на пересмотр в v2: если будет реальная потребность в кастомизированных demo-данных, можно перейти на runtime-генерацию через Web Worker.

**Alternatives considered:**
- **Runtime-генерация на клиенте** — отклонено, добавляет ~100-150 строк JS, требует знания распределений, для v1 не нужно.
- **Один универсальный demo-csv** — отклонено, не покрывает разные metric_type.
- **Не делать demo-csv вообще** — отклонено, нубам реально нужно проверить, что пайплайн работает, без подключения продакшена.

**Related:**
- `NOTEBOOK_TEMPLATES.md` — секция «Схема данных, которую ожидает ноутбук»
- ADR-008 (тур) — параллельное решение, demo-csv это не часть тура

## ADR-006 — Статусы плана draft/approved с readonly после approve

**Date:** 2026-05-14
**Status:** Accepted

**Context:**
В первой версии флоу тест-план и конструктор ноутбука были на одном шаге. Когда вынесли конструктор в отдельный шаг (ADR-005), возник вопрос: что мешает пользователю утвердить план, собрать ноутбук, вернуться на план, изменить metric_type — и получить рассогласование между планом и ноутбуком, который уже скачан?

**Decision:**

1. План имеет два статуса: `draft` (можно править, скачивать, загружать отредактированный) и `approved` (заморожен).

2. На шаге плана появляется кнопка `✓ Утвердить план`. После нажатия:
   - `state.plan.status = approved`
   - Бриф (шаг 1) переключается в readonly-режим
   - Шаг 3 (конструктор) разблокируется

3. Чтобы вернуться к редактированию, пользователь должен явно нажать `↻ Вернуть в черновик` с подтверждением «текущая конфигурация ноутбука будет сброшена».

4. Поле `status: draft | approved` живёт в YAML frontmatter `test_plan.md` и переносимо между сессиями.

**Consequences:**
- Невозможно случайно рассогласовать план и ноутбук.
- Если пользователь загружает чужой план — он попадает с `status: approved` (раз уже утверждён), сразу на конструктор.
- Минус UX: если пользователь хочет «поправить мелочь» в плане после approve — придётся явно вернуть в draft и пересобирать ноутбук. Это сознательный trade-off в пользу консистентности.

**Alternatives considered:**
- **Без статусов, план всегда редактируемый** — отклонено, см. context.
- **Конфигурация ноутбука сохраняется и переносится при возврате в draft** — отклонено для v1, усложняет логику; если эффект, что нужно «слегка поправить», окажется частым — пересмотрим.

**Related:**
- ADR-002 (артефакты как переносимое состояние) — `status` это часть переносимого состояния
- ADR-005 (5-шаговый флоу)

## ADR-005 — 5-шаговый флоу с развилкой на старте

**Date:** 2026-05-14
**Status:** Accepted

**Context:**
Изначально флоу был 4-шаговый: Бриф → Тест-план (+ конструктор ноутбука) → Анализ → Read-out. По мере проработки стало ясно две вещи:

1. Тест-план и конструктор ноутбука — это разные смысловые штуки. План — это документ для обсуждения с аналитиком, имеющий ценность сам по себе. Конструктор — это инструмент сборки кода. Совмещение в одном шаге перегружало правую колонку UI.

2. Реальный сценарий: PM прошёл бриф один раз, обсудил план с аналитиком, ушёл на две недели — а сессия в браузере уже потеряна. Тул как «инструмент, который помнит» не делаем (см. ADR-001 no backend). Но `test_plan.md` может выступать в роли переносимого состояния — если пользователь его загрузит, не нужно проходить бриф заново.

**Decision:**

1. Флоу — 5 шагов: **Бриф → Тест-план → Конструктор → Анализ → Read-out**, плюс стартовый экран.

2. На стартовом экране — развилка: «Начать с брифа» (полный путь) или «У меня уже есть план» (загрузить `test_plan.md`, попасть сразу на конструктор).

3. При загрузке плана бриф восстанавливается из YAML frontmatter и доступен для просмотра/возврата (но в режиме readonly, см. ADR-006).

4. Шаги залочены по умолчанию: 3 разблокируется после approve плана (ADR-006), 4-5 — по очереди.

**Consequences:**
- Test_plan.md становится «точкой входа» для команд, использующих stat·plan на пол-пути.
- UI чище: на шаге плана только план + оценка, на шаге конструктора только ячейки + demo-csv.
- Минус: добавляется ещё один шаг в степпере, визуально цикл выглядит длиннее. Решили, что это окей — каждый шаг имеет одну чёткую цель.

**Alternatives considered:**
- **Остаться при 4 шагах с совмещённым планом+конструктором** — отклонено, перегруженный UI и нет возможности пропустить бриф при возврате.
- **Сделать конструктор сабшагом плана (tab внутри)** — отклонено, путает навигацию: пользователь не понимает, утвердил он план или нет.
- **Точка входа «загрузить план» как отдельная страница вне основного флоу** — отклонено, фрагментирует UX.

**Related:**
- ADR-002 (артефакты как переносимое состояние)
- ADR-006 (статусы плана)
- `FLOW.md`

## ADR-004 — Тул не принимает продуктовых решений

**Date:** 2026-05-14
**Status:** Accepted

**Context:**
По ходу обсуждения возникали идеи добавить в тул логику принятия решений: «катить или нет», «обещай ROI», «дай рекомендацию». Соблазн велик — пользователь устал, он хочет ответ. Но это противоречит сути инструмента: stat·plan не знает контекста бизнеса (стоимость деплоя, конкурентная среда, ожидания инвесторов), и любая «рекомендация» будет ложно-объективной.

Параллельный соблазн: использовать LLM для интерпретации результатов («ваш тест успешен, потому что…»). LLM может ошибиться в интерпретации p-value, проигнорировать SRM, не учесть guardrails.

**Decision:**

1. Тул проверяет **формальные условия** (decision rules из плана):
   - CI пересекает 0 или нет
   - Нижняя граница CI выше порога SHIP
   - Guardrails нарушены или нет

2. На основе этих проверок показывает **«рекомендуемое решение»** (SHIP / ITERATE / KILL), но это **рекомендация на основе правил, которые написал пользователь сам в плане**, а не суждение тула.

3. Финальное поле «Принятое решение» в read-out **пустое и заполняется руками**.

4. **LLM в продакшен-флоу не используется** — все правила детерминированные и проверяемые.

**Consequences:**
- Пользователь не может «делегировать» решение тулу — это сохраняет ответственность за человеком.
- В UI многократно повторяются формулировки типа «решение остаётся за тобой», «обсуди с аналитиком». Это сознательная риторика, не словесный мусор.
- Тул не зависит от LLM API, нет проблем с rate limits, стоимостью, приватностью.
- Не делаем feature «объясни мне результат» через LLM в v1.

**Alternatives considered:**
- **LLM для интерпретации результатов** — отклонено, см. context.
- **Embedded chatbot «спроси про мой тест»** — отклонено, нет надёжного способа гарантировать качество ответов на статистические вопросы.
- **«Уверенность тула в решении» как численная метрика** — отклонено, всё та же ложная объективность.

**Related:**
- ADR-003 (структурная оценка) — родственное решение про «не оценивать качество»
- Принцип 3 в `concept.md`

## ADR-003 — Структурная оценка плана вместо оценки качества

**Date:** 2026-05-14
**Status:** Accepted

**Context:**
В одной из ранних итераций обсуждалась идея «качества гипотезы 78%» как часть скоринга. Стало ясно, что это ложная объективность — невозможно алгоритмически оценить «хорошесть» продуктовой гипотезы без понимания бизнес-контекста.

Та же проблема стояла шире: оцениваем ли мы «качество брифа» как полноту заполнения, или есть что-то более глубокое?

**Decision:**

1. **Оцениваем только структуру, не содержание:**
   - Полнота: заполнены ли обязательные поля
   - Консистентность: согласуется ли test_method с metric_type, реалистичен ли MDE при заданном baseline, достижим ли sample size

2. **Бриф не имеет численной оценки**, только индикатор заполненности `N/10 вопросов`. Оценка появляется только когда есть готовый тест-план.

3. **Гипотеза проверяется на 4 структурных слота** (изменение / метрика / направление / механизм) через эвристики. Не оценивает «глубину» или «оригинальность» — только наличие слотов.

4. **Все правила открыты** — пользователь видит, что засчитывается и почему. Никаких «секретных формул».

**Consequences:**
- Скоринг честный и предсказуемый: пользователь понимает, что нужно сделать для повышения скора.
- Не пытаемся быть умнее, чем мы есть. Тул не критикует идеи PM — только структуру.
- Замечания типа «MDE 8% rel. оптимистичен при baseline 3.1%» — это формальное правило, не суждение. Можно объяснить, почему так.

**Alternatives considered:**
- **NLP-оценка качества гипотезы через LLM** — отклонено, см. ADR-004.
- **Большой опросник «качества» с весами** — отклонено, неотличимо от ложной объективности.
- **Не оценивать вообще, только чек-листы pass/fail** — рассматривается как кандидат, см. open question в concept.md.

**Related:**
- `SCORING.md` — все правила скоринга
- ADR-004 (тул не принимает решений)

## ADR-002 — Артефакты как переносимое состояние, строгий YAML frontmatter

**Date:** 2026-05-14
**Status:** Accepted

**Context:**
Без бэкенда (ADR-001) встаёт вопрос: как сохранять состояние между сессиями? localStorage работает в рамках одного браузера, но реальный сценарий — PM прошёл бриф, ушёл на две недели, открыл тул на другом компе. Тул не помнит. При этом мы хотим, чтобы пользователь мог продолжить работу.

Решение лежит на поверхности: артефакт сам является состоянием. `test_plan.md` содержит всё необходимое для восстановления контекста. Но это требует строгого формата — иначе парсинг ломается.

**Decision:**

1. Все ключевые артефакты (`brief.md`, `test_plan.md`, `validation.md`, `readout.md`) имеют **обязательный YAML frontmatter** с заданной схемой.

2. **Парсинг строгий (путь A):** при загрузке `test_plan.md` ожидаются именно те поля и в той структуре, которые описаны в `DATA_MODEL.md`. Невалидные файлы отклоняются с понятной ошибкой («не могу распарсить, проверь шапку YAML»).

3. **Markdown-секции после frontmatter** дублируют ключевые поля для человеческой читаемости, но при парсинге приоритет у frontmatter.

4. **Общий `test_id`** связывает все артефакты одного теста — это позволяет проверить консистентность пакета.

**Consequences:**
- Тест-план становится переносимым состоянием: скачал → отправил → загрузил у другого пользователя → продолжаешь работу.
- Это разблокировало развилку на старте (ADR-005).
- Минус: пользователь не может писать план в свободной форме. Решили, что это нормально — план это формальный документ, а не proseca.
- Аналитики, которые правят план вручную, должны не сломать YAML. Это требует дисциплины, но markdown + YAML — стандартная практика для technical docs (как в hugo/jekyll).

**Alternatives considered:**
- **Мягкий парсинг (путь B):** принимать любой md, выдирать поля по эвристикам — отклонено, непредсказуемо и пользователь не понимает, почему его план «не догрузился».
- **JSON как основной формат вместо md** — отклонено, md лучше для human-readability и для отправки коллеге.
- **Бэкенд с базой тестов** — отклонено, см. ADR-001.

**Related:**
- `DATA_MODEL.md` — полная схема YAML
- ADR-005 (5-шаговый флоу с развилкой)

## ADR-001 — No backend, всё на клиенте

**Date:** 2026-05-14
**Status:** Accepted

**Context:**
Базовое архитектурное решение, определяющее всю последующую разработку. Альтернативы рассматривались: SaaS-сервис с бэкендом, гибрид (бэк для тяжёлых вычислений, фронт для UI), полный self-hosted.

Главные критерии:
- Это личный pet-проект (Костя), не корпоративный продукт
- Целевая публикация — GitHub Pages, бесплатно
- Целевая аудитория — продакт-менеджеры, не data engineering команды
- Нет ресурсов на поддержку инфраструктуры

**Decision:**

1. **Всё работает на клиенте** — HTML, CSS, vanilla JS (или с лёгкой реактивной либой вроде Alpine.js).

2. **Деплой — GitHub Pages.** Никаких серверов, баз данных, авторизации.

3. **Состояние** — в localStorage между шагами одной сессии. Между сессиями — через переносимые артефакты (см. ADR-002).

4. **Тяжёлые вычисления** (полноценный pandas/scipy, симуляции, ML) — не делаются в браузере. Они уходят в **генерируемый ноутбук**, который пользователь запускает у себя.

5. **Зависимости — минимум:** js-yaml, simple-statistics (или собственные хелперы), JSZip, опционально D3/Chart.js.

**Consequences:**
- Невозможны фичи, требующие сервера: логин, шаринг, командная работа, история тестов, интеграции с внешними системами (BigQuery, Mixpanel).
- Возможны фичи, не требующие сервера: парсинг csv до 50MB, расчёт sample size, скоринг плана, генерация ipynb.
- Стоимость поддержки = 0. Любой может форкнуть.
- Нет аналитики использования (если только не подключить что-то вроде Plausible — но это противоречит духу).
- Pyodide рассматривался — отклонён, 10MB рантайма ради scipy.stats это оверкилл (см. ADR-009).

**Alternatives considered:**
- **SaaS с бэком (FastAPI + Postgres)** — отклонено, требует поддержки, противоречит pet-проекту.
- **Self-hosted Docker** — отклонено, поднимает порог входа для пользователя.
- **Гибрид (тяжёлые расчёты в облаке)** — отклонено, добавляет latency и зависимости.

**Related:**
- `ARCHITECTURE.md` — полный стек
- `concept.md` — принцип №1
- ADR-002 (артефакты как переносимое состояние) — следствие no backend
