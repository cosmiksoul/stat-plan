# Scoring

## Принципы

1. **Структурная, не качественная.** Оцениваем наличие обязательных секций и консистентность выбранных методов. Не пытаемся оценить «хороша ли продуктовая гипотеза» — это не наше дело.
2. **Прозрачная.** Пользователь видит, какие правила сработали и почему скор такой. Никаких «секретных формул».
3. **Один скор на стадии тест-плана.** Бриф оценивается только по проценту заполнения (это не «качество», а индикатор «можно ли уже жать дальше»). Полноценный скоринг появляется только когда есть готовый тест-план.

## Формула

```
total_score = hypothesis_score (20) 
            + design_completeness_score (30) 
            + methodological_consistency_score (30) 
            + data_peek_score (20)
```

Максимум — 100. Веса предварительные, могут пересматриваться (см. `OPEN_QUESTIONS.md`).

## Группа 1. Полнота гипотезы (макс 20)

Проверяет 4 структурных слота:

| Слот | Очки | Эвристика |
|------|------|-----------|
| Изменение | 5 | Найден текст между «если» и «то/запятой» |
| Метрика | 5 | Найдена метрика (по словарю или по совпадению с `state.brief.metric_name`) |
| Направление + Δ | 5 | Найден глагол направления (вырастет/упадёт) и число с % или единицей |
| Механизм | 5 | Найден текст после «потому что» |

Если эвристика не нашла слот — 0 очков. Если нашла — 5.

## Группа 2. Полнота дизайна (макс 30)

Проверяет наличие обязательных полей в `test_plan.md`:

| Поле | Очки | Условие пасса |
|------|------|---------------|
| `metric_type` | 3 | Задан, входит в enum |
| `test_method` | 3 | Задан, входит в enum |
| `randomization_unit` | 3 | Задан, входит в enum |
| `mde` | 3 | Задан, value > 0 |
| `alpha`, `power` | 3 | Заданы, в разумном диапазоне (alpha 0.01–0.1, power 0.7–0.95) |
| `sample_size_per_arm` | 3 | Задан, > 0 |
| `duration_days` | 3 | Задан, > 0 |
| `guardrails` (≥ 1) | 3 | Хотя бы один guardrail |
| `stop_conditions` (≥ 1) | 3 | Хотя бы одно условие остановки |
| `decision_rules` (≥ 2) | 3 | Заданы правила для минимум 2 исходов |

## Группа 3. Методологическая консистентность (макс 30)

Это самая ценная часть скоринга — здесь тул проверяет, что выбранные методы согласованы.

| Правило | Очки | Условие |
|---------|------|---------|
| Test method подходит под metric type | 6 | См. матрицу ниже |
| MDE реалистичен | 6 | `mde.value < 50` для relative_percent; для absolute_pp — `< baseline * 2` |
| Sample size достижим | 6 | `sample_size_per_arm / (daily_traffic / 2) ≤ 14` дней |
| Baseline разумный | 4 | Для proportion: `0.001 < baseline < 0.999`; для continuous: ненулевой |
| Guardrails не противоречат main metric | 4 | Если guardrail метрика совпадает с main metric — warning |
| Variance reduction обоснован | 4 | Если выбран CUPED, должна быть указана базовая ковариата |

### Матрица консистентности metric_type ↔ test_method

| metric_type ↓ \ test_method → | z_test_prop | t_test | welch | mannwhitney | bootstrap | delta |
|-------------------------------|-------------|--------|-------|-------------|-----------|-------|
| proportion                    | ✓           | ⚠      | ⚠     | ✗           | ✓         | ✗     |
| continuous                    | ✗           | ✓      | ✓     | ✓           | ✓         | ✗     |
| ratio                         | ✗           | ⚠      | ⚠     | ⚠           | ✓         | ✓     |
| count                         | ⚠           | ⚠      | ⚠     | ✓           | ✓         | ✗     |

- ✓ — полные очки (6)
- ⚠ — половина очков (3) + warning «лучше использовать X»
- ✗ — 0 очков + warning «неподходящий метод»

## Группа 4. Pre-flight на данных (макс 20)

Зависит от того, загрузил ли пользователь данные на этапе Data Peek.

| Проверка | Очки | Условие пасса |
|----------|------|---------------|
| Данные загружены | 5 | `data_peek.uploaded == true` |
| Baseline сошёлся с введённым пользователем | 5 | Разница < 20% |
| Распределение метрики проверено | 5 | `data_peek.distribution_check == ok` |
| Стабильность во времени проверена | 5 | CV метрики по дням < 0.3 |

Если данные не загружены — 0 за эту группу. Это не критично, но без data peek скор не будет > 80.

## Интерпретация скоров

- **≥ 90** — план готов к запуску, обсуждать особо нечего.
- **70–89** — план хороший, есть мелкие замечания. Обсуди с аналитиком пункты с warning.
- **50–69** — план есть, но методология или полнота под вопросом. Обязательно ревью.
- **< 50** — план сырой, отправка на запуск преждевременна.

**Важно.** Скор — это индикатор, не приговор. Тест может быть отличным с скором 75 (например, нет data peek потому что метрика новая) и плохим с 95 (например, баг в эвристике засчитал слот гипотезы, которого нет).

## Пересчёт

Скор пересчитывается реактивно на любое изменение `state.brief` или `state.plan`. Это включает:
- Изменение ответа в брифе при возврате назад
- Загрузку отредактированного `test_plan.md`
- Загрузку csv для data peek

В JSON состояния хранится последний посчитанный скор и breakdown — это позволяет включить snapshot в YAML frontmatter `test_plan.md` (информационно, при парсинге обратно игнорируется).
