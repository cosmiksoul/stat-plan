# Туториалы

> Три сквозных сценария — от брифа до HTML-отчёта. По 7-10 минут на проход. Каждый сценарий — типовая продуктовая ситуация с готовым CSV.

## Зачем это нужно

stat·plan покрывает три семейства метрик: **proportion** (конверсия), **continuous** (среднее: ARPU, время на сайте), **ratio** (отношение: CTR per user, sessions per visit). Под каждое — свой статистический критерий и свой набор подводных камней. Туториалы дают почувствовать продукт через типовую ситуацию каждого типа, чтобы потом ты пришёл со своими данными уверенно.

**Что понадобится:**
- Аккаунт [Google Colab](https://colab.research.google.com) (бесплатный) или локальный Jupyter
- Один из demo CSV — скачивается прямо со страницы конструктора в шаге 3 (или [здесь](#demo-данные))
- 7-10 минут на каждый сценарий

**Как пользоваться:** идёшь по сценарию от начала до конца, повторяя ответы из таблиц. Если хочешь — отклонись и подставь свои значения, посмотри как меняется результат. Каждый сценарий самодостаточный: можно начать с любого.

## Сценарий 1 — Конверсия (proportion) → SHIP

### Контекст

Маркетинг переделал onboarding-флоу первого депозита. Гипотеза: новый флоу повысит конверсию в first deposit на **≥10% rel**. Baseline CR ≈ 3%.

В CSV — реально прогнанный тест, где Δ ≈ +29% rel (намного сильнее MDE). Должен дать p ≪ 0.05 → SHIP. Туториал показывает «зелёный» путь — как выглядит явно успешный тест.

### Шаг 01 — Бриф

Стартовый экран → **«Начать с брифа»**. Ответы:

| Q | Поле | Значение |
|---|---|---|
| Q01 | Цель теста | **Изменение продукта (фича, UX)** (preselect) |
| Q02 | Гипотеза | `Если переделать onboarding-флоу первого депозита, то конверсия first deposit вырастет на 10% rel, потому что меньше дроп-офф на шаге подтверждения` |
| Q03 | Тип метрики | **Конверсия / proportion** |
| Q04 | Название метрики | `First deposit conversion` |
| Q04 | Колонка в CSV | `cr_first_deposit` |
| Q05 | Baseline | `0.031` |
| Q06 | Единица рандомизации | **Пользователь** (preselect) |
| Q07 | MDE | `10`, единицы `Относительный %` |
| Q08 | Доступный трафик | `1000` пользователей/день |
| Q09 | Guardrails | `bounce_rate`, направление `max`, threshold `5`, единицы `relative_percent` |
| Q10 | Stop & Decision rules | defaults |

Под Q08 увидишь расчёт: **sample size ≈ 3 500-4 000 на ветку**, длительность **~7-8 дней**, метод `z_test_proportions`.

### Шаг 02 — Утвердить план

На `/step2` — preview test_plan.md слева, оценка справа. Score должен быть в диапазоне **80-95/100**. Кликни **«✓ Утвердить план»**.

### Шаг 03 — Скачать ноутбук

На `/step3` оставь все обязательные ячейки включёнными. Опционально включи `segments` (сегментный анализ — по любой категориальной колонке, в demo есть `day`). Нажми **«↓ Скачать ipynb»**.

Можно зайти в «Ожидаемую схему данных» внизу страницы и переименовать колонки под имена в твоём хранилище — мы тут оставим как есть, имена совпадают с demo CSV.

### Шаг 04 — Выполнить в Colab

1. Открой [colab.research.google.com](https://colab.research.google.com) → File → Upload notebook → выбери `analysis.ipynb`.
2. На левой панели Colab → Files → Upload → выбери `demo_proportion.csv`.
3. В первой code-cell измени `CSV_PATH = 'experiment_results.csv'` на `CSV_PATH = '/content/demo_proportion.csv'`.
4. **Runtime → Run all** (Ctrl+F9). Все ячейки выполнятся за ~10-30 секунд.
5. Последняя ячейка (с тегом `stat-plan-results`) покажет JSON со всеми метриками: `control_n: 4500`, `treatment_n: 4500`, `delta_rel: ~28`, `p_value: <0.001`, `ci_lower/upper > 0`, `significant: true`.
6. **File → Download → Download .ipynb** — сохрани локально.

### Шаг 05 — Загрузить отчёт

На `/step4` (Stepper → «04 Валидация и отчёт»):

1. **Drag-drop** выполненный `.ipynb` на upload-зону.
2. Зелёный бейдж «✓ Результаты извлечены» — парсер нашёл ячейку с тегом `stat-plan-results`.
3. Все 6 секций ниже заполняются автоматически:

| Секция | Что увидишь |
|---|---|
| **2. Результаты** | Significant badge зелёный, NOVELTY badge зелёный «not detected» |
| **3. Sanity checks** | SRM ✓, sample size ≈ план ✓, направление ✓ (positive, как ожидали) |
| **4. Decision rules** | SHIP auto-eval сработал (CI > 0, нижняя граница ≥ +5% rel) |
| **5. Графики** | 4-6 PNG: balance (counts + means), SRM (observed vs expected 50/50), main_test errorbar Δ vs 0, guardrails |
| **6. Скачать** | 3 кнопки blue: report.html / readout.md / .zip |

4. Кликни **«↓ Скачать report.html»**, открой в браузере.
5. Финальный шаг: в dropdown «Принятое решение» руками выбери **SHIP** — это твоё решение, тул только подсказал рекомендацию.

**Что узнал из сценария:** полный успешный тест от брифа до отчёта. Видишь как работают decision rules (нижняя граница CI положительная → SHIP сработал), что входит в HTML отчёт (TL;DR + графики + проверки здравомыслия), почему «принятое решение» остаётся за PM.

## Сценарий 2 — Средняя величина (continuous) → INCONCLUSIVE

### Контекст

Команда добавила новый ценовой блок на checkout. Гипотеза: новый блок повысит **ARPU** на ≥5% rel. Baseline ARPU ≈ 100₽.

В CSV — тест прошёл **недо-power'ленный**: реальный эффект ~1.6%, что меньше MDE. Туториал показывает inconclusive verdict — самый частый случай в реальности.

### Шаг 01 — Бриф

| Q | Поле | Значение |
|---|---|---|
| Q01 | Цель | **Изменение продукта** |
| Q02 | Гипотеза | `Если показать новый ценовой блок на checkout, то ARPU вырастет на 5% rel, потому что лучше воспринимаемая ценность` |
| Q03 | Тип метрики | **Средняя величина (continuous)** |
| Q04 | Название | `ARPU` |
| Q04 | Колонка | `arpu` |
| Q05 | Baseline | `100` (для continuous без dropdown — просто number) |
| Q06 | Randomization unit | **Пользователь** |
| Q07 | MDE | `5`, единицы `Относительный %` |
| Q08 | Daily traffic | `1000` |
| Q09 | Guardrails | `time_on_site`, направление `min`, threshold `10`, единицы `relative_percent` |
| Q10 | defaults | |

**Внимание на Q07:** для continuous и ratio тул покажет встроенное пояснение — расчёт размера выборки приближённый без Data Peek (σ неизвестна, используется bootstrap-приближение ±20-30%).

**Опционально** на Q08 раскрой Data Peek → загрузи `demo_continuous.csv` → получишь точный расчёт через t-test без предупреждения о приближении. Baseline и σ посчитаются автоматически.

**Ожидаемый расчёт без peek:** ~5000 на ветку, длительность ~10 дней, метод `t_test`.

### Шаги 02-04

Утверди план → /step3 → скачай ipynb → Colab → upload `demo_continuous.csv` → измени `CSV_PATH` → Run all.

**Ожидаемые числа в export-cell:**
```json
{
  "control_n": 5000,
  "treatment_n": 5000,
  "delta_rel": ~1.6,           // в %
  "p_value": >0.1,              // not significant
  "ci_lower": <0,               // отрицательная нижняя граница
  "ci_upper": >0,               // CI пересекает 0
  "significant": false
}
```

### Шаг 05 — Загрузить отчёт

| Секция | Что увидишь |
|---|---|
| **2. Результаты** | Significant badge **жёлтый** «Not significant (p ≈ 0.24)» |
| **3. Sanity checks** | SRM ✓, sample size match ✓, направление ✓ (positive но слабый) |
| **4. Decision rules** | Ни SHIP, ни KILL не сработали → «Решение остаётся за PM». Можно вручную поставить ITERATE |
| **HTML отчёт TL;DR** | `⚠ Not statistically significant (p = 0.24, α = 0.05). Δ rel = +1.6%, 95% CI [−1.14, 4.58] (абс. разность, ед. arpu)` |

**Что узнал:** как выглядит inconclusive — CI пересекает 0, decision rules не дают однозначной рекомендации, PM решает сам (продлить тест? добавить вариант? убить гипотезу?). Это **типичный** результат — не каждая гипотеза побеждает.

## Сценарий 3 — Отношение (ratio) → WINNER

### Контекст

Партнёрский баннер на странице товара. Гипотеза: новый баннер повысит **CTR на партнёрский клик** на ≥15% rel. Baseline CTR ≈ 9% (clicks / sessions per user).

В CSV — реальный Δ ≈ +23% rel. Туториал показывает работу с **ratio-метрикой**: числитель и знаменатель — это разные единицы (clicks per session, агрегированные на пользователя). Здесь срабатывает delta method (или bootstrap-приближение без peek).

### Шаг 01 — Бриф

| Q | Поле | Значение |
|---|---|---|
| Q01 | Цель | **Изменение продукта** |
| Q02 | Гипотеза | `Если показать новый партнёрский баннер на странице товара, то CTR на партнёрский клик вырастет на 15% rel, потому что выше CTA visibility` |
| Q03 | Тип метрики | **Ratio (числитель/знаменатель из разных юнитов)** |
| Q03.1 | numerator | `clicks` |
| Q03.1 | denominator | `sessions` |
| Q04 | Название | `Partner CTR` |
| Q04 | Колонка | `partner_ctr` (агрегированная — не нужна в CSV, считается из numerator/denominator) |
| Q05 | Baseline | `0.09` |
| Q06 | Randomization unit | **Пользователь** |
| Q07 | MDE | `15`, единицы `Относительный %` |
| Q08 | Daily traffic | `500` пользователей/день |
| Q09 | Guardrails | можно пропустить |
| Q10 | defaults | |

**Опционально** на Q08 раскрой Data Peek → загрузи `demo_ratio.csv` → точный расчёт через delta method. Без peek будет предупреждение о bootstrap-приближении.

### Шаги 02-04

Утверди план → /step3 → **обрати внимание:** в Expected schema будут **две** колонки `clicks` и `sessions` (не одна `partner_ctr`). Это особенность ratio. Скачай ipynb → Colab → `demo_ratio.csv` → Run all.

**Ожидаемые числа:**
```json
{
  "control_n": 3500,
  "treatment_n": 3500,
  "delta_rel": ~22,            // +22% rel
  "p_value": <0.01,
  "ci_lower": >0,
  "ci_upper": >0,
  "significant": true
}
```

### Шаг 05 — Отчёт

| Секция | Что увидишь |
|---|---|
| **2. Результаты** | Significant badge зелёный |
| **3. Sanity checks** | SRM ✓ (3500/3500), total_n match ✓ |
| **4. Decision rules** | SHIP сработал |
| **HTML отчёт TL;DR** | `✅ Statistically significant. Δ rel = +22%, CI [+13%, +31%] (абс. разность ratio), p < 0.01` |

**Что узнал:** ratio-метрика требует **двух колонок** в CSV (числитель + знаменатель), агрегация на уровне рандомизации (на пользователя). Delta method даёт точный CI; без него — bootstrap-приближение с предупреждением. Decision rules работают так же как для proportion, но семантика «нижняя граница CI» — в единицах разности ratio, не в процентах от baseline.
