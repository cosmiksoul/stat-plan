# С чего начать

> Что такое stat·plan, как устроен его флоу и какие артефакты получает на выходе продуктовый менеджер.

## Что это

**stat·plan** — открытый клиентский инструмент для планирования и валидации A/B-тестов. Помогает продуктовому менеджеру пройти полный цикл — от формулировки гипотезы до пост-анализа — без необходимости вручную выбирать статистический критерий и без риска получить методологически сломанный тест.

A/B-калькуляторов в интернете много, но почти все упираются в две фундаментальные проблемы. Первая — методологическая слепота калькулятора: он не знает про right-skewed распределения, zero-inflation в ARPU или sample ratio mismatch и спокойно предлагает t-test там, где нужен Welch или bootstrap CI. Вторая — высокий порог входа: чтобы корректно выбрать критерий и понять допущения, пользователю нужно отлично знать прикладную статистику. stat·plan закрывает обе проблемы через дерево вопросов с минимальным ветвлением, структурную оценку плана и генерируемый ноутбук с правильным набором проверок под конкретный сценарий.

Принципиально продукт **не пытается быть SaaS** — нет логина, бэкенда, истории тестов. Всё работает на статических файлах GitHub Pages, артефакты — обычные `.md` / `.ipynb` / `.csv`, которые можно открыть, отредактировать руками, закоммитить в git, отправить в Confluence. Это и техническое решение, и философское: пользователь владеет своими данными.

## Флоу из 4 шагов

| Шаг | Что происходит | Артефакт на выходе |
|---|---|---|
| **01 Бриф** | 10 вопросов: цель → гипотеза → метрика → baseline → единица рандомизации → MDE → трафик → guardrails → decision rules. На каждом шаге — расчёт размера выборки и длительности теста на лету. Опционально: загрузка CSV для уточнения baseline и σ. | внутреннее состояние |
| **02 Тест-план** | Предпросмотр сгенерированного `test_plan.md` с YAML-блоком и оценкой 0-100. Замечания по группам критериев. Можно скачать, отдать аналитику на ревью, получить обратно отредактированную версию и подгрузить — оценка пересчитается. | `test_plan.md` |
| **03 Конструктор** | Набор ячеек ноутбука под выбранную методологию: загрузка → balance → SRM → novelty → main_test → guardrails → segments → export. Опциональные ячейки переключаются. Редактируемая схема данных — под имена колонок в твоём хранилище. | `analysis.ipynb` (+ опционально demo CSV) |
| **04 Валидация и отчёт** | Перетащи выполненный ноутбук — парсер достанет результаты из ячейки с тегом `stat-plan-results`, графики из `plt.show()` встроятся в HTML-отчёт. Автоматические проверки (SRM, размер выборки vs план, направление эффекта). Decision rules из брифа применяются автоматически — генерируется параграф «Recommended next step». Финальное «Принятое решение» заполняешь сам. | `report.html`, `readout.md`, `analysis.zip` |

**Ключевая идея:** stat·plan **не пересчитывает** статистику — это была бы циркулярная валидация (тестировать наш код нашим же кодом). Он считает один раз — в ноутбуке у пользователя — а потом помогает корректно интерпретировать результат.

## Шаг 01 — Бриф

10 обязательных вопросов с мягкой валидацией (не блокирует переход, только подсказывает). На каждом — предвыбран разумный вариант по умолчанию, можно принять нажатием Enter.

- Q01 Цель теста (продуктовое изменение / контент / алгоритм / маркетинг / другое)
- Q02 Гипотеза по шаблону «если … то … потому что …» — парсер проверяет 4 слота
- Q03 Тип метрики: proportion / continuous / ratio / count
- Q04 Название метрики + код колонки в CSV
- Q05 Baseline (в подходящих единицах)
- Q06 Единица рандомизации: user / session / cluster
- Q07 MDE (relative % или absolute)
- Q08 Доступный трафик в день
- Q09 Guardrails (минимум один, с дефолтами bounce_rate / time_on_site)
- Q10 Stop conditions + Decision rules

Под Q08 — реактивный размер выборки + длительность теста + используемый метод. Если рассчитанная выборка не помещается в доступный трафик — встроенное предупреждение.

**Опциональный Data Peek** — раскрывается под расчётом. Можно загрузить CSV с историческими данными, тул посчитает реальный baseline, σ (для continuous), ratio variance через delta method, проверку распределения (skewness/kurtosis), стабильность по дням (CV). После peek расчёт размера выборки становится точным — пропадает предупреждение о приближённости.

## Шаг 02 — Тест-план

Превью сгенерированного `test_plan.md` слева, оценка плана справа.

Оценка 0-100 разбита на 4 группы:
- **Полнота гипотезы** (20 баллов) — заполнены ли все 4 слота шаблона
- **Полнота дизайна** (30 баллов) — baseline, MDE, sample size, guardrails, decision rules
- **Методологическая консистентность** (30 баллов) — соответствие выбранного метода типу метрики, отсутствие приближений если есть данные
- **Pre-flight на данных** (20 баллов) — был ли Data Peek, совпадает ли реальный baseline с заявленным

Под каждой группой — список конкретных замечаний с severity (info/warn/critical). Кликаешь по группе — раскрывается чек-лист.

Действия: **Скачать** test_plan.md, **Загрузить** отредактированный (от аналитика), **Утвердить план**, **Вернуть в черновик**. После утверждения бриф переходит в режим только-чтения; разблокируется Шаг 03.

## Шаг 03 — Конструктор

Информация об утверждённом плане (test_id, метрика, метод, sample size, длительность, α/power) — сверху страницы.

**Обязательные ячейки** (включены, нельзя отключить): загрузка данных + EDA, SRM check, баланс группы, novelty effect, основной тест (выбирается по `plan.test_method`), guardrails, export tagged cell.

**Опциональные**: сегментный анализ (по любой категориальной колонке — geo, device, plan, CRM-метка), bootstrap CI.

**Скоро** (заглушки): CUPED variance reduction, delta method для ratio (полная реализация).

**Demo CSV** — справа: 3 готовых файла по типам метрик (proportion, continuous, ratio), чтобы проверить что ноутбук работает на демо-данных перед прогоном на своих. Файлы те же, что используются в туториалах.

**Редактируемая схема данных** — таблица колонок, которые ожидает ноутбук. Можно прямо в строке переименовать колонку под имя в своём хранилище, поменять тип, добавить/убрать опциональную колонку. Изменения применяются к Python-коду ноутбука при скачивании.

В footer'е — `Скачать analysis.ipynb` (blue) + `К валидации →` (green primary).

## Шаг 04 — Валидация и отчёт

Перетаскиваешь выполненный `.ipynb` в окно загрузки. Парсер находит ячейку с тегом `stat-plan-results`, достаёт JSON с результатами (control_n, treatment_n, delta_rel, p_value, ci_lower, ci_upper, srm_pvalue, novelty_flag, significant, control_mean, guardrails). Все `plt.show()` графики из ноутбука извлекаются как base64 PNG и встраиваются прямо в HTML-отчёт (файл получается самодостаточный — открывается оффлайн без подключения к интернету).

На странице 6 секций:

1. **Загрузка** — зона перетаскивания + запасной вариант с ручным вводом
2. **Результаты** — 8 полей формы (предзаполнены из ipynb, любое поле можно переопределить) + бейджи значимости и novelty
3. **Sanity checks** — SRM (chi² на размеры групп), размер выборки vs план, направление эффекта vs MDE direction
4. **Decision rules** — парсер из брифа автоматически применяет правила (поддерживает unicode-операторы `≤≥−`, русские «нижняя/верхняя граница», unit-aware `% rel` через baseline). Сработавшие правила отмечены автоматически; нераспознанные — отмечаешь руками
5. **Графики из ноутбука** — 4-6 PNG (balance, SRM, главный тест с CI vs 0, guardrails, novelty)
6. **Скачать артефакты** — `report.html` (самодостаточный, открывается оффлайн), `readout.md` для вики, `analysis.zip` с полным пакетом

Внизу — `Новый тест` (amber reset) + sticky `Скачать всё (.zip)` (blue).

## Артефакты

| Файл | Где генерируется | Зачем |
|---|---|---|
| `test_plan.md` | Шаг 02 | Документ для команды/Confluence. YAML frontmatter + markdown секции. Round-trip — можно загрузить обратно, бриф восстановится. |
| `analysis.ipynb` | Шаг 03 | Jupyter-ноутбук с правильной методологией под план. 13-15 ячеек: загрузка → проверки → главный тест → экспорт. Ячейка с тегом `stat-plan-results` — контракт для парсера на Шаге 04. |
| `report.html` | Шаг 04 | Самодостаточный HTML-одностраничник с TL;DR, встроенными графиками, проверками здравомыслия и применёнными decision rules. Открывается в любом браузере, печатается в PDF. |
| `readout.md` | Шаг 04 | Markdown для вики/Confluence с YAML-блоком и структурированными разделами. Поле `decision: ""` — заполняется руками. |
| `analysis.zip` | Шаг 04 | Полный пакет: test_plan.md + analysis.ipynb + report.html + readout.md. Один файл — в Confluence-страницу. |

Все артефакты связаны общим `test_id` в YAML frontmatter — склеиваются в логический набор теста.

## Принципы продукта

1. **No backend.** Всё в браузере. Никакого логина, базы, истории. localStorage хранит активный тест, после `↺ Начать сначала` — чистый стейт.
2. **Артефакты — обычные файлы.** Md, ipynb, csv, html, zip. Их можно открыть, отредактировать, закоммитить в git, отправить коллеге. Артефакт = переносимое состояние.
3. **Тул не принимает продуктовых решений.** Не говорит «катить или нет». Проверяет полноту плана и методологическую консистентность, считает CI и p-value — финальное решение всегда за человеком.
4. **Структурная оценка, не оценка качества мысли.** Скоринг проверяет наличие обязательных секций и консистентность выбранных методов. Не пытается оценить «хороша ли твоя продуктовая гипотеза» — это не наше дело.
5. **Открытость данных и правил.** Пользователь видит, какие правила применяются и почему. Все формулы расчётов задокументированы в [методологии](/docs/methodology).
6. **Минимум ветвлений в брифе.** Бриф — это вход для PM, не для статистика. 10 вопросов, минимум обязательных полей, дефолты везде где разумно. Сложности (α/power, CUPED, стратификация) спрятаны в «продвинутые параметры».

## Что мы НЕ делаем

- ❌ Не интегрируемся с BigQuery / Amplitude / Mixpanel — пользователь сам выгружает CSV
- ❌ Не храним историю тестов — каждый прогон stateless
- ❌ Не делаем sequential testing / mSPRT с always-valid CI в v1
- ❌ Не делаем библиотеку прошлых тестов / поиск по похожим экспериментам — это уже SaaS
- ❌ Не используем LLM в процессе подготовки тест-плана и ноутбука — все правила детерминированные и проверяемые
- ❌ Не пересчитываем Δ/p/CI из CSV (circular validation) — доверяем результату из твоего ноутбука

Полное обоснование — в разделе [«Что мы НЕ делаем» методологии](/docs/methodology#что-мы-не-делаем).
