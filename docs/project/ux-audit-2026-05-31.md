## A. Функция «? Включить тур» — broken contract (P1)

### Что нашёл в коде

| Где | Что есть |
|---|---|
| `state/reducer.js:117` | `tourEnabled: false` в `initialState` |
| `state/reducer.js:134, 219-220` | `TOGGLE_TOUR` action, переключает boolean |
| `components/Header.jsx:44-55` | Кнопка toggle с label `? Включить тур` ↔ `✕ Закрыть тур` |
| `App.jsx:36-37` | `document.body.classList.toggle('tour', state.tourEnabled)` |
| `styles/index.css:21-23` | Color tokens `--color-tour` / `--color-tour-soft` / `--color-tour-hover` (только для самой кнопки) |

### Что НЕ нашёл

- **0 селекторов `body.tour ...`** в CSS — класс на body вешается, но никаких rules под него нет
- **0 компонентов** типа `TourTip`, `TourPlate`, `TourOverlay` — плашки никогда не были созданы
- **0 контента** для тура — какие шаги показывать, в какой последовательности, что объяснять

### Вывод

**Кнопка «? Включить тур» — broken contract.** Меняет цвет (становится pressed), переключает label, добавляет класс на body — но **на экране ничего не происходит**. Пользователь жмёт → ноль обратной связи.

Это **хуже, чем отсутствие кнопки**: создаёт ложное обещание «у нас есть туториал», ломает доверие при первом клике.

**Подтверждение из CONTEXT.md (Sprint 1 timeline):**
> «Тур-режим (toggle класса работает; плашек самих нет)»
> «Тур сквозной (state внутри сессии работает; плашек самих нет)»

То есть **известный gap с Sprint 1**, который мы не закрыли за 6 спринтов. Теперь продукт «готов» (Sprint 7 CLOSE), а сломанная кнопка осталась в шапке.

### Варианты решения

| Подход | Усилия | Pros | Cons |
|---|---|---|---|
| **A. Убрать кнопку** | 5 мин | Честно, ничего не обещаем | Теряем future hook для онбординга |
| **B. Заменить на onboarding modal** «1 экран» (что есть тут, как работает) | ~1.5-2 ч | Решает основную задачу — «новый пользователь не понимает с чего начать» | Не тур, но похоже |
| **C. Сделать настоящий тур** (5-7 tour-плашек с подсветкой ключевых элементов) | ~3-4 ч | Полноценный onboarding | Больше usage, библиотека/самописное (~30-50 строк CSS-overlay + steps array + reactive position) |
| **D. Перенаправить на NotebookLM** «CRO эксперт» как onboarding | ~10 мин | Использует ресурс из Sprint 9 plans | Не про сам tool — про методологию |

**Рекомендую B** (onboarding modal): быстрее туровых плашек, решает реальную задачу «куда я попал и что делать», не требует поддержки реактивных tooltips при изменении layout. Тур (C) — over-engineering для линейного 4-шагового флоу.

## B. UX-инконсистентности между шагами

Сравнение на основе 4 скриншотов:

### B.1. Page header style (P1)

| Шаг | H1 | Subtitle | Status badges | Action справа |
|---|---|---|---|---|
| 1 Бриф | — нет H1 — | — | — | — (только Header restart/tour) |
| 2 Тест-план | «Тест-план» | «Сгенерирован из брифа. Проверь, скачай, утверди — это разблокирует следующий шаг.» | ↳ ЗАГРУЖЕН, ✓ УТВЕРЖДЁН | — |
| 3 Конструктор | «Конструктор ноутбука» (в карточке с метриками) | — | ↳ ЗАГРУЖЕН, ✓ УТВЕРЖДЁН | — |
| 4 Валидация и отчёт | «Валидация и отчёт» | «Прогнал тест, выполнил ноутбук — перетащи .ipynb сюда и получи HTML-отчёт для стейкхолдеров за 3 секунды.» | — | ↺ Сбросить результаты |

**Проблемы:**
- Шаг 1 **без H1** — выбивается из ритма (на других шагах H1 «якорь» сверху страницы)
- Шаг 4 **без status badges** — нет визуальной симметрии с шагами 2/3
- «↺ Сбросить результаты» на Шаге 4 — единственный action в этой позиции, новый паттерн

**Рекомендация:** На Шаге 1 добавить H1 «Бриф» с subtitle типа «Опиши тест в 10 вопросах — sample size и план посчитаются автоматически». Badges на Шаге 4 пока не нужны (никаких «approved» state там нет), но **место для action справа** можно унифицировать — например status badge `↑ ЗАГРУЖЕН: filename.ipynb` после upload.

### B.2. Status badges (P2)

| Badge | Где | Когда |
|---|---|---|
| `↳ ЗАГРУЖЕН` | Шаги 2, 3 | если `state.plan.editedExternally = true` (план загрузил извне) |
| `✓ УТВЕРЖДЁН` | Шаги 2, 3 | если `status: approved` |

**Проблема:** semantics слова `ЗАГРУЖЕН` неочевиден. Можно прочесть как «план загружен в систему» (что happen'ется всегда), а имеется в виду «загружен из внешнего файла, а не из брифа». Контекст «↳» (impl) помогает, но не сильно.

**Рекомендация:** `↳ ИЗ ФАЙЛА` или `↑ ЗАГРУЖЕН ИЗВНЕ` — более явно.

### B.3. Banner style и context (P2)

| Шаг | Banner |
|---|---|
| 1 | accent green border, status info + action link «↗ К ТЕСТ-ПЛАНУ» |
| 2 | accent green border, status info + button «У меня есть выполненный ноутбук →» |
| 3 | **НЕТ banner'а** — нет напоминания «план утверждён» |
| 4 | dark / neutral banner с **объяснением цели страницы** (другая роль) |

**Проблемы:**
- Шаг 3 теряет статус-контекст (что план утверждён). Если пользователь пришёл на Шаг 3 из закладки в браузере — он не видит badge approval'а в banner-формате (только в карточке метрик далеко справа).
- Шаги 1-2 используют banner для «status + action», Шаг 4 — для «what is this page» description. **Разные роли banner'а, но визуально похожи.**

**Рекомендация:**
- Добавить banner на Шаг 3 (или симметричную row с status), если план approved
- Разделить визуально «status banner» (зелёный border) и «info banner» (нейтральный border) — например иконкой ℹ vs ✓

### B.4. Footer style (P2)

| Шаг | Footer |
|---|---|
| 1 | 1 кнопка справа «ДАЛЬШЕ →» |
| 2 | 4 кнопки в группе слева/центр + 1 справа («ПЕРЕЙТИ К КОНСТРУКТОРУ») |
| 3 | 1 link слева («← К ПЛАНУ») + 1 secondary центр («К ВАЛИДАЦИИ →» — Sprint 7 G-3) + 1 primary справа |
| 4 | **НЕТ footer'а** — все actions в section 6 (3 download кнопки) |

**Проблема:** на Шаге 4 нет восстанавливающей рамки страницы. Когда контент scrolled далеко вниз, нет sticky bottom bar с примаркой «здесь финал». На других шагах footer создаёт «edge» страницы.

**Рекомендация:** на Шаге 4 — sticky bottom bar с «Скачать всё (.zip)» как primary action, дублирующий section 6 button. Это даст:
- Симметрию с шагами 1-3 (всегда есть finish-action внизу)
- UX — пользователь не должен скроллить вверх к section 6 чтобы скачать после редактирования результатов

### B.5. Reset action — два разных reset на Шаге 4 (P2)

На Шаге 4 одновременно:
- В Header: `↺ НАЧАТЬ СНАЧАЛА` — **полный reset** (clearState + RESET_STATE + redirect to /)
- В page header: `↺ Сбросить результаты` — **локальный reset** только results section

**Проблема:** две кнопки с **одинаковой иконкой ↺** и похожими подписями. Пользователь может перепутать «начать сначала» (теряет ВСЁ) с «сбросить результаты» (теряет только step 4 ввод).

**Рекомендация:**
- Изменить иконку «Сбросить результаты» → например `✕ Очистить форму` или `🗑 Reset upload` — другая иконка, явный scope
- Или поставить ConfirmDialog с явным «Удалить только результаты Шага 4? Бриф и план останутся.»

### B.6. Numbering в секциях (P3, OK)

Шаг 4 нумерует секции `1. Загрузи...`, `2. Результаты`, ..., `6. Скачать артефакты`. Шаги 1-3 не нумеруют.

**Это OK** — на Шаге 4 много секций в одной странице, нумерация помогает ориентироваться. На других шагах одна-две колонки, нумерация не нужна.

### B.7. Шаг 3 — двойная информация «↳ ЗАГРУЖЕН / ✓ УТВЕРЖДЁН» (P3)

На Шаге 3 status badges повторяют то же, что на Шаге 2. Это OK для consistency, но **на Шаге 3 нет button «Вернуть в черновик»** — пользователь должен идти на Шаг 2 чтобы это сделать. **Информация про статус есть, action — нет.**

**Рекомендация:** оставить badges, ничего не делать (action на Шаге 2 — правильное место).

### B.8. Слова «УТВЕРЖДЁН», «ЗАГРУЖЕН» — caps lock везде (P3, OK)

Stat·plan UI использует ALL CAPS для mono-label badges, что согласуется с palette/font. Хорошо.

## C. Не-инконсистентности (false alarms)

- **Layout columns разный по шагам** (Шаг 1 = question+map, Шаг 2 = preview+scoring, Шаг 3 = cells+csv, Шаг 4 = single column) — **OK**, разные шаги решают разные задачи.
- **Stepper indicator** (green underline + jirний цифра текущего, ✓ chip для пройденных) — consistent, не трогаем.
- **Primary accent button color** (`bg-accent`) везде одинаковый — consistent.
- **Border-only secondary** vs **link-only tertiary** — consistent hierarchy.
