# Sprint 1 — Foundation + Start Screen + Step 1 Skeleton

**Type:** Code sprint
**Estimated:** 4-5 дней работы

---

## Overview

Первый спринт проекта. Закладываем структуру SPA, делаем стартовый экран с развилкой, степпер на 5 шагов, и пустую страницу шага 1 (бриф) — но без вопросов. Цель — получить деплой на GitHub Pages с видимым скелетом, на котором можно навигировать между «старт → шаг 1» и понять блокировку остальных шагов.

**Никакой логики обработки данных в этом спринте нет.** Парсинг md, localStorage, реальные вопросы брифа — это будущие спринты.

### 2. Реализовать `index.html`

Single-page application. Один HTML-файл с тремя секциями (или больше — на твоё усмотрение), переключающимися через JS:

- Шапка приложения (всегда видна): логотип/название, кнопка `? Включить тур` (на эту итерацию — toggle класса `body.tour`, без логики плашек; работающие плашки — будущий спринт)
- Контейнер для основного контента (меняется в зависимости от текущего шага)

Стартовый экран (отображается когда `state.started == false`):

- Заголовок и краткое описание (взять из `README.md` первый абзац, без фанатизма)
- Две карточки бок о бок:
  - «Начать с брифа» — кнопка
  - «У меня уже есть план» — карточка с drag-and-drop зоной (визуально готова, но при дропе файла показывает только сообщение «Парсинг загруженного плана будет реализован в Sprint 2/3. Пока используй "Начать с брифа".»)

Страница шага 1 (Бриф) — отображается когда `state.started == true && currentStep == 1`:

- Слева/в центре — placeholder «Здесь появятся вопросы брифа. Реализация — следующий спринт.»
- Справа — карта вопросов (10 пунктов из `docs/context/BRIEF_TREE.md`):

### 3. Реализовать `assets/app.js`

- Один JS-файл, vanilla (без сторонних библиотек)
- In-memory state: `const state = { started: false, currentStep: 1 }`
- Hash-routing: `#/` (стартовый экран), `#/step1` (шаг 1). Шаги 2-5 — URL-ы не реализуем в этом спринте.
- Обработка `hashchange` + ручная установка хэша при кликах
- Если URL = `#/step1` но `state.started == false` — перекинуть на `#/` (FLOW.md, секция «Переходы»)
- Функция render() переключает видимость секций и пишет хэш
- Drag-and-drop обработчик на правой карточке стартового экрана: при дропе показывает сообщение-заглушку (см. выше), state не меняется

### 4. Реализовать `assets/styles.css`

Базовый CSS для всего того, что появилось в этом спринте. Дизайн-направление — посмотри `mockups/ab_planner_mockup_v4.html` как референс (открывается в браузере отдельным файлом). **Не пытайся скопировать мокап один-в-один** — достаточно близкого ощущения. Палитра, шрифты, отступы — на твоё усмотрение, но единообразно.

Обязательное в этом спринте:
- Степпер выглядит как степпер (5 пунктов в ряд с разделителями, текущий выделен, заблокированные приглушены)
- Карточки стартового экрана крупные, кликабельные
- Drag-and-drop зона визуально отличается от обычной карточки (пунктирная рамка)
- Прогресс-бар — полоска с заливкой
- Карта вопросов — компактный список с номерами

Не обязательное (deferred):
- Mobile responsive (можно declare desktop-only в этом спринте)
- Тёмная/светлая тема — пока одна (можно выбрать любую, светлая проще)

## Technical Notes

### Состояние

In-memory объект, описано выше. **Не сохраняем в localStorage.** Это сознательно — реализация хранилища через localStorage — отдельная задача, в этом спринте состояние пропадает при перезагрузке (что нормально, потому что нет вопросов, нет данных к сохранению).

### Hash-routing

Простой подход: слушать `hashchange`, парсить `location.hash`, маршрутизировать. Не использовать History API (это требует server-side fallback, которого на GitHub Pages нет).

### Зависимости

**Никаких сторонних JS-библиотек.** Не подключай Alpine.js, не подключай js-yaml, не подключай Chart.js. Всё это придёт в будущих спринтах, когда станет реально нужно. См. ADR-001, принцип «зависимости — минимум».

### Шапка приложения

В шапке должна быть кнопка `? Включить тур`. По клику переключает класс `body.tour`. На этом всё — содержимое тур-плашек реализуется в отдельном спринте. ADR-008 определяет финальное поведение (плашки сверху на каждом шаге), но в Sprint 1 достаточно self-toggling кнопки без эффекта.

### Дизайн

Не вкладывай много времени в визуальный полиш. Приоритет — рабочая навигация и понятная структура. Тонкая настройка дизайна будет в отдельном спринте после того как появится больше контента.

## Acceptance criteria (smoke-тест)

1. Открыть деплой на GitHub Pages → виден стартовый экран: заголовок, описание, две карточки. Степпер НЕ виден.
2. В шапке видна кнопка `? Включить тур`. Клик переключает класс `body.tour` (визуальное состояние — на твоё усмотрение, важно что toggle работает).
3. Клик «Начать с брифа» → переход на шаг 1, URL меняется на `#/step1`. Виден: степпер (текущий = «Бриф»), прогресс-бар «0/10», основное место с placeholder-текстом, справа — карта вопросов из 10 пунктов.
4. В степпере шаги «Тест-план», «Конструктор», «Анализ», «Read-out» приглушены, курсор `not-allowed`, клик ничего не делает.
5. Перейти вручную на URL `…/#/step1` (с обновлением страницы) — перекидывает обратно на стартовый экран (потому что state не сохранён).
6. На карточке «У меня уже есть план» зона drag-and-drop принимает файл, показывает сообщение-заглушку «Парсинг будет в Sprint 2/3», не падает с ошибкой, state не меняется.
7. Открыть в Chrome и Firefox — выглядит корректно. Safari опционально (если есть mac).
